## 意图锚点（每次迭代前必读）

本 skill 守护一条主线：**让已有 skill 在长期迭代中保持好用，而不是在修补中漂移。** 迭代的目标是每次运行走同样的过程，而不是每次产出同样的文本。

改动护栏：
- 复发模式才立为规则；单次失败只进观察名单
- 上下文先删减后拆分；拆分走完删减、压缩、脚本化之后才轮到
- 每次改动过回归对比再合并；无对比的结论记为"待验证"，不记为"改进"
- 改动附带证据（一次真实返工或一条测试失败）；无证据的批评进观察名单

## 核心工作流

每次迭代按四步执行，顺序不可跳过：

### 1. 诊断到机制层，再动手

AI 修 skill 的失败几乎都源于在文本层修补机制层问题。先对照下表定位：

| 症状 | 真正的病灶层 | 错误修法 |
|---|---|---|
| 不触发 / 过触发 | frontmatter description 的判别逻辑 | 改正文、堆触发关键词 |
| 频繁要求人工确认 | 授权边界与默认值缺失 | 删除"请确认"话术 |
| 上下文臃肿 | 冗余内容与自由度错配 | 直接拆分 |
| workflow 越改越臃肿 | 状态写进了文本，而非锚定在产物上 | 继续加状态与转移 |
| 移植后过触发、规则异物感 | 搬运了文本而非机制，源场景词汇残留 | 事后逐个清理触发词 |
| 越优化问题越多 | 审查驱动的无证据改动循环，每次修复制造新问题 | 继续发起下一轮"优化" |
| 越改越难用 | 补丁堆积、规则互相牵扯 | 继续打补丁 |

### 2. 证据闸与改动意图

**无证据，不动手。** 改动必须附带证据：一次真实返工，或一条测试集失败。"帮我优化一下"是无判据指令——审查可以发起，但产出分级：

- 阻断性项（有失败证据支撑）→ 立即修
- 理论性项（无事故记录，仅"不够完善"）→ 记入证据日志的观察名单，等真实使用提供证据；不落地为改动

**冻结状态：** 冒烟集通过 + 最近约 10 次使用零返工的 skill 视为冻结；无使用日志时以"用户确认近期使用均无返工"为替代判据。冻结 skill 只接受修复请求，不接受优化请求。正在被使用的 skill，最大风险不是不够完善，而是永不稳定。

然后用一句话写清本次改动要解决的模式（不是个案），并预判它可能破坏什么。无法写出这句话，说明还在修症状，回到第 1 步。

### 3. 执行修改

改动优先级默认为：description 措辞 > 删冗余内容 > 压缩措辞 > 结构调整。不在此列的改动多为加法，先过审计四问。

- 触发、上下文、授权、workflow 结构、措辞的设计原理 → 读 [../shared/design-principles.md](../shared/design-principles.md)（创建与审查共用）；若文件不可得，用下方审计四问兜底
- 从其他仓库提取优势 → 见「移植纪律」
- 测试集建设 → 见 [../shared/testing-guide.md](../shared/testing-guide.md)

**审计四问**：

1. 没有这句，模型也会做对吗？ → 删
2. 模型知道但会忘？ → 压成清单短句
3. 模型不知道？ → 写成明确知识
4. 必须每次精确一致？ → 挪进 scripts

### 4. 回归对比与减法审查

- 改动后必须用测试集做新旧版本对比，无对比不合并；尚无测试集时，至少重跑触发本次改动的那条失败输入，并按「冷启动」补建冒烟集
- 每加一条规则，检查是否有因此可删的旧规则
- 定期（每 5–10 轮迭代）整体重构，把补丁压回干净结构

## 冷启动（没有日志、没有测试集时）

本 skill 的典型第一现场是一个没有任何日志与测试集的 skill。不要一次建成完整证据体系，按以下顺序起步：

1. **投诉即第一份证据**：用户的返工/异常反馈就是一次真实返工，已满足证据闸，不必等日志
2. **先建冒烟集**：从本次投诉与历史对话中摘 3–5 条输入（真实语料原样摘录，方法见 ../shared/testing-guide.md），预置在固定目录
3. **回归基线从简**：改动后至少重跑触发改动的失败用例 + 冒烟集；全量对比等测试集长大后再说
4. **证据日志从一个追加式 markdown 文件起步**（格式与分区见「证据体系」），不需要 hook；hook 与定时任务等真实返工咬过人再建（见 references/harness.md）

## 证据体系

证据强度按改动的粘性配比：

- **可逆采纳**（进参考文件、按需查阅）：社区验证的经验直接采用，不设闸
- **升格进正文**（成为强制规则、永久占用上下文）：社区验证降低门槛但不取消，需一次本地确认。规则进得来就很少出得去，所以升格闸要严
- **升格由真实事故拉动**：事故发生、且本可由某条参考层原则防止 → 该原则升入正文；参考层原则长期与任何事故无关 → 移出候选。两个方向都不需要监控执行过程

**观测分工**（用户只看结果，其余皆 agent 的活）：

- 记录：机制层 hook 自动捕获工件侧事件（会话/加载/改动，落 `skill-事件日志.jsonl`，落地实例见 references/harness.md）；对话内事件（返工标记等 hook 够不着的）仍由 agent 追加
- 失败感知：用户的返工冲动（零成本、自动上报）；会话内被返工时 agent 主动标记
- 取证：agent 按本 skill 工作流执行——调日志，区分指针故障（参考文件没被读）与内容故障（读了但没守住），修法不同
- 升格提议：agent 按判据提出，用户一字批准

**证据日志**：skill 工作区固定一个 `skill-证据日志.md`，追加式、一行一条，写入者是 agent（执行后告知级）。四个分区：

1. **观察名单**：理论性项 + 来源 + 待验证缺口
2. **返工事件**：日期 | skill | 症状 | 疑似病灶层——升格的唯一合法证据源
3. **升格 / 移出**：内容 + 依据，引用返工事件日期，让每条正文规则可追溯"它为什么存在"
4. **冻结状态**：skill | 冻结日期与判据

回归基线只留当前版本快照，随接受的改动覆盖，不搞无限历史；冻结 skill 的早期事件行可定期归档压缩成一行总结。

观测基础设施（hooks、定时任务、三层分工）见 references/harness.md——被真实返工咬过再建，不预防性建设。

## 移植纪律（从其他仓库/skill 提取优势时）

"提取优势"失败的标准模式：搬运了文本而非机制——优势是语境依赖的，拔出即死，且源仓库的场景词汇被一并带入，成为外来触发点（过触发的常见来源）。必须改为机制移植：

1. **先诊断，后提取**：用一句话声明目标 skill 的具体缺口。写不出缺口声明，不发起提取
2. **找机制，不找段落**：定位源仓库靠什么解决该问题（一条判别边界、一个产物断言、一种默认值），提取机制本身
3. **翻译，不誊写**：机制在目标语境重新实例化；源语境的专有名词、触发词、示例、路径、工具名全部重写为目标侧自己的语料——外来触发点在这一步系统性消灭
4. **合入后过双关**：审计四问 + 触发测试集（验证未引入过触发）

## AI 协作的四个已知偏差（审查时主动对抗）

让 AI 修改 skill 或生成测试时，默认它有以下倾向，逐条检查：

1. **加法偏好**：倾向于追加规则而非删减重构——要求它先给出删除方案
2. **教科书化**：生成的测试输入是完整规整的需求文档腔，不是真人口吻——要求模仿真实语料（见 ../shared/testing-guide.md）
3. **拆分偏好**：把"优化上下文"执行成拆分——要求它先走完删减与压缩路径
4. **形式化偏好**：把 workflow 的严谨性执行成状态机、转移表等工程外观——要求锚定产物而非状态（见 design-principles.md 的 Workflow 结构）

## 完整示例（一次迭代）

- **返工事件**：用户合并三份表格，结果漏了一个 sheet，返工一次（记入证据日志·返工事件）
- **诊断**：不是措辞问题——加"下次别漏 sheet"是空提醒，不改变任何行为。真实缺口是模型不知道"先清点源文件、确认数量再合并"这条私有约定 → 属审计四问的"模型不知道 → 写成明确知识"
- **修改**：加一句"多文件时先列出文件与 sheet 清单，确认总数后再合并"；同时删掉一条因此冗余的格式说明（减法）
- **回归**：该输入入冒烟集，新旧对比：旧版漏 sheet、新版通过，其余三条核心用例不变 → 合并，升格依据记入证据日志

## 测试集速览

完整指南在 ../shared/testing-guide.md。最易忘的两条：

- 输入来自真实语料原样摘录（含口语、错字、半截话），AI 只做扰动不做创作
- 断言针对交付物价值（"用户拿到可直接使用"），而非步骤服从；冒烟集 15 分钟内跑完
