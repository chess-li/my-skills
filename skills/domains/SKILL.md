# 统一语言维护

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**让项目拥有一套人、代码、AI 三方共用且歧义最小的领域词汇，消除讨论与实现间的理解偏移。** 统一语言是活的，随领域模型演进持续修订，不是写完即冻结的文档。

改动护栏：
- 先查已有术语再讨论、再命名；不重复造已有概念的词
- 术语选择目标是"团队内歧义最小"，不是"命名学上最正确"
- 改动术语表与改动代码一样走 review，防止悄悄腐烂
- 无真实歧义信号不主动扩张术语表，避免建成无人维护的巨文件

## 核心工作流

### 1. 先读现状

任何涉及领域概念的讨论或命名前：

1. 读项目根目录 `DOMAINS.md`（总览+索引）
2. 按索引进入相关上下文文件：跨模块上下文在 `docs/contexts/<限界上下文>/<限界上下文>-domains.md`，模块私有上下文在模块目录下的 `DOMAIN.md`
3. 若文件不存在，按「冷启动」初始化，而不是凭记忆继续

### 2. 选词优先级

为新概念选词，或裁定一词多义时，按以下顺序：

1. **代码事实/项目事实**：已发生的命名优先保持一致。但要区分"好事实"和"坏遗产"——代码命名已偏离领域含义时，以当前领域理解为准重构代码并更新术语表，不让坏命名绑架语言
2. **行业规范/行业共识**
3. **社区规范/社区共识**
4. **法规事实**：金融、医疗、政务等强合规领域中，法规定义的概念是不可改名的硬约束，此时其优先级高于行业惯例
5. **自造词**：垫底，但新概念确实无现成词时果断造词并立即写进术语表，比硬套旧词好

同优先级内出现候选冲突时，选团队内歧义最小的那个。

### 3. 沉淀时机

出现以下信号即应沉淀（写入或修订术语表），不要等"稳定了再写"：

- 同一概念出现多种叫法
- 讨论中反复出现歧义或误解（含与 AI 的理解偏移）
- 领域建模讨论（事件风暴等）产出关键概念后，即时记录
- 需要在代码、文档、AI 提示词间保持一致时

### 4. 写入规范

- **词条格式**（轻量，四要素）：术语 + 定义 + 所属限界上下文 + 反例（易混淆的相近概念）
- **消费者闭环**：新增/修订词条时指明消费端落点（哪个 skill/文档正文将使用该词），同会话落地并验证；指不出消费者 → 不立词条，记观察名单
- **位置归属**：跨模块/全局上下文写入 `docs/contexts/<限界上下文>/<限界上下文>-domains.md`；仅属于单一模块的上下文就近写入该模块目录的 `DOMAIN.md`——离代码近，改代码时顺手维护，不容易腐烂
- **索引同步**：新增上下文文件或重要术语后，同步更新根目录 `DOMAINS.md` 的索引，保证单入口可达
- **引用保障**：确认 `AGENTS.md` / `CLAUDE.md` 引用了 `DOMAINS.md`，确保 AI 会话一定会加载

## 冷启动（项目还没有领域文档时）

不要一次建成完整体系，按以下顺序起步：

1. 从本次讨论/命名冲突中提取 3–5 个最关键概念，先建根目录 `DOMAINS.md` 最小术语表
2. 只有一个上下文时不拆子文件；出现第二个上下文再拆 `docs/contexts/<限界上下文>/`
3. 在 `AGENTS.md` 中加一行引用
4. 术语表随真实歧义信号增长，不预防性扩张

## 完整示例（一次命名裁定）

- **现场**：讨论中出现"订单"、"工单"、"任务单"三种叫法指同一概念
- **读现状**：`DOMAINS.md` 无此词条；代码中 `Order` 类已存在且语义一致 → 属代码事实优先级
- **裁定**：定为"订单（Order）"，写入术语表，注明反例："工单"特指售后场景的另一概念，不混用
- **收尾**：更新 `DOMAINS.md` 索引；若代码中存在 `TaskOrder` 残留命名，列入重构待办
