# Bug 诊断与修复

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**未定位根因，不动手修复。** 修复的目标是消除根因，不是让症状消失。

诊断护栏：
- 先复现：没有稳定的复现，不诊断、不修复；复现不出来 → 向用户要复现条件（输入、环境、日志），不猜测
- 根因的通过判据 = 解释 + 预测：能解释从根因到症状的完整路径，能预测同一根因还会产生的其他症状；解释不了 → 找到的仍是症状节点，继续追
- 根因有层次：期望（该有的行为定义错或未定义）、设计（技术决策本身缺陷）、实现（代码偏离期望与设计）。先判层，再决定修复走哪条路
- 修复 = 消除根因：想加特判分支、吞异常、用默认值绕过的那一刻，正是根因未除的信号——退回上一步重新定位
- 找到根因后全局搜索同一根因的其他发生点；修这一类，不只修被报告的这一处
- 调试或测试本地接口/服务 = 本流程走到验证闭环（含实现层修复）；不因「调试」停在观察
- bug 承载于 issue：报告 bug → 先走 issues skill 落 issue（category: bug，创建前检索防重复）

## 核心工作流

### 1. 建立红色回路并复现

取得一个已经实际运行过、能捕获用户原始症状的复现手段。首选顺序是：失败测试、HTTP 脚本、CLI 加固定输入、浏览器脚本、真实记录回放、最小 harness；间歇性问题再用 property/fuzz、版本对比或二分。人手操作是最后手段，也要用脚本固定步骤和输出。

红色回路的完成物必须同时满足：

- 走真实 bug 路径，并断言用户说的具体症状，不只断言「没有报错」
- 已运行至少一次，记录命令与关键输出
- 结果可重复、运行够快、可由 agent 无人值守执行

把命令、输入与环境、关键输出和最小场景写入 bug issue 的「复现记录」；聊天中的摘要不替代 issue 记录。

只有满足这三点，才进入根因定位。回路过慢或信号过宽时，先缩小输入、依赖和断言；没有红色回路，不凭代码猜根因。

取得红色回路后重复运行，确认失败就是用户描述的失败。前会话或 issue 中的根因/修法只当线索，本会话未复现则未定位。

逐项删减输入、调用者、配置和步骤，每次只删一项并重跑，直到得到仍然失败的最小场景。最小场景转成修复后的回归验证，不保留无关噪声。

- 可复现 → 第 2 步
- 不可复现 → 向用户要具体复现条件（输入、环境、日志/报错）；仍不可复现 → 停下告知用户，不猜测改代码
- 测试先行/验收闭环中的预期失败（功能尚未实现）不是 bug → 退出本流程，回 tdd/implement 循环
- 本地接口/服务/试运行（用户给了地址、线索是本地接口失败、或用户要本地验证）：复现 = 对实际服务打该接口，单测不算。无地址 → local-env skill 立通道取 url。通道不立（端口没听、代理 502、进程已死）→ 同样走 local-env。禁止用运行时诊断代替立通道。失败或不符承诺 → 把原始响应（状态与 body）给用户看，再进第 2 步

### 2. 定位根因

先列出 3–5 个按可能性排序的可证伪假设，并为每个假设写出会使回路变绿或变红的预测。把列表交给用户查看；用户暂时不在场时按当前排序继续，不等待表态。按预测逐个验证，每次只改变一个变量。产物：一句话根因陈述 + 证据（file:line 或复现输出）。

追读进入依赖包内部时，按序定位源码：先全局搜本机工作区，无果则问用户源码位置；再无则读依赖自带的 sources；只能反编译时，先用构建工具依赖树确认项目实际解析的版本，反编译该版本——不取默认最新版。

自检：该根因能解释全部症状吗？能预测其他症状吗？不能 → 继续追。

### 3. 判层与路由

- 实现层：期望与设计都对，代码偏离（含：配置、spec 或 design 已写 X、代码做 Y）→ 第 4 步。默认自动修，不询问、不问「修哪一层」；修复方案不互斥则都做
- 设计层：技术决策本身缺陷，逐个打补丁修不完 → 先走 design skill 修订设计，再回第 4 步
- 期望层：行为未定义或定义本身有错 → 停下问用户期望什么行为；项目有 spec 则先走 spec skill 更新，再回来。用户已给出目标或 spec 已断言该行为 → 不是本层
- 方向分叉：判层定「哪层错」不定「修成什么样」；互斥修复方向的产品可观察面不同（能力范围、数据面、资源模型）→ 列候选停下问用户（interview skill），不静默自选；「spec 已断言」只用于定层，不免除本步；「修这一类」扩复到未报修的能力同样先问
- 项目没有 spec/design 文档 → 按"期望行为 vs 实现方式"直接判断，不强行建文档

### 4. 修复

遵循 tdd skill：先写复现 bug 的失败测试，再写消除根因的最小实现。复现测试留下作回归测试。

### 5. 验证闭环

- 复现测试转绿，相关测试通过
- 复现是对本地地址的请求时：同一条请求再打到符合承诺或用户目标。本变更若被该地址上的进程经本地依赖仓库加载 → 先刷新该仓库再重启，刷新不留给用户。需要重启 → local-env skill 立通道，不留给用户。探测到可连或用户说已重启后立刻再打，不等「继续」
- 对照定位根因时预测的"其他症状"逐一检查：均已消除
- 该 bug 的 issue 归档：status 改 archived、移入 `docs/issues/<限界上下文>/archive/`、记变更历史并同步 guide 状态表（有则）（git 仓库并提交）；走了 implement 流程的由那边归档，不重复
- 告知用户结论：根因一句话、属哪一层、修了什么
