# Bug 诊断与修复

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**未定位根因，不动手修复。** 修复的目标是消除根因，不是让症状消失。

诊断护栏：
- 先复现：没有稳定的复现，不诊断、不修复；复现不出来 → 向用户要复现条件（输入、环境、日志），不猜测
- 根因的通过判据 = 解释 + 预测：能解释从根因到症状的完整路径，能预测同一根因还会产生的其他症状；解释不了 → 找到的仍是症状节点，继续追
- 根因有层次：期望（该有的行为定义错或未定义）、设计（技术决策本身缺陷）、实现（代码偏离期望与设计）。先判层，再决定修复走哪条路
- 修复 = 消除根因：想加特判分支、吞异常、用默认值绕过的那一刻，正是根因未除的信号——退回上一步重新定位
- 找到根因后全局搜索同一根因的其他发生点；修这一类，不只修被报告的这一处

## 核心工作流

### 1. 复现

取得一个稳定失败的复现手段：测试用例、命令或操作步骤。

- 可复现 → 第 2 步
- 不可复现 → 向用户要具体复现条件（输入、环境、日志/报错）；仍不可复现 → 停下告知用户，不猜测改代码
- 测试先行/验收闭环中的预期失败（功能尚未实现）不是 bug → 退出本流程，回 tdd/implement 循环

### 2. 定位根因

从失败点沿调用链/数据链向上追，直到第一个出错的点。产物：一句话根因陈述 + 证据（file:line 或复现输出）。

自检：该根因能解释全部症状吗？能预测其他症状吗？不能 → 继续追。

### 3. 判层与路由

- 实现层：期望与设计都对，代码偏离 → 第 4 步
- 设计层：技术决策本身缺陷，逐个打补丁修不完 → 先走 design skill 修订设计，再回第 4 步
- 期望层：行为未定义或定义本身有错 → 停下问用户期望什么行为；项目有 spec 则先走 spec skill 更新，再回来
- 项目没有 spec/design 文档 → 按"期望行为 vs 实现方式"直接判断，不强行建文档

### 4. 修复

遵循 tdd skill：先写复现 bug 的失败测试，再写消除根因的最小实现。复现测试留下作回归测试。

### 5. 验证闭环

- 复现测试转绿，相关测试通过
- 对照定位根因时预测的"其他症状"逐一检查：均已消除
- 告知用户结论：根因一句话、属哪一层、修了什么
