# 代码库讲解

本 skill 守护一条主线：**让读者得到可工作的代码模型，而不是文件名摘要。** 解释必须从真实入口追到输出，所有关键断言都带文件和符号位置。

## 解释模式

### 1. 收口问题并判断复杂度

复述你对范围的理解。单个函数、单个模块或窄调用链走简单路径；跨模块、跨服务或完整架构走复杂路径。范围有歧义时先声明假设再探索，不用猜测填补事实。

### 2. 探索真实路径

简单问题由当前会话直接读取入口、调用者、被调用者、数据类型和测试。复杂问题分成 2–4 个不重复的角度，派只读探索者分别检查数据模型、运行链路、边界和配置；每个探索者必须返回读过的文件、追到的输入到输出路径和非显然陷阱。

### 3. 综合解释

把探索结果合成一条连贯路径。冲突回到代码核对；找不到证据的地方写明未知，不把文件名当行为证据。

### 4. 交付解释

按需要包含以下部分：

- **概览**：它解决什么问题，为什么存在
- **关键概念**：读者必须知道的类型、服务和边界
- **工作过程**：从触发、数据流、决策点到输出
- **文件位置**：入口、核心实现、测试和配置
- **易错点**：隐含前提、反直觉行为和已知尖角

每个关键行为都附 `file:line` 或函数、类型名称。完成标准是：读者能据此找到入口并描述一次完整运行路径。

## 交互式解释 HTML

当用户要求“生成可交互的 HTML 来解释核心设计/代码”时，`how` 仍是主 skill。这个产物是代码事实的解释投影，不是产品界面原型：不要求先造视觉变体，也不把交互语义分岔交给用户选择。只有用户另外要求探索产品界面方向或对齐视觉效果时，才转入 `prototype`。

按以下顺序生成并核对：

1. 建立证据映射：概念 → 代码符号/`file:line`；生命周期状态和分支 → 实际状态、错误或恢复路径；术语 → `DOMAINS.md` 词条。页面只引用词条，不为同一概念另立定义。
2. 先写当前实现，再单独标记设计目标和未知项。只有覆盖当前成功路径及关键失败、撤销、恢复分支时，才把范围称为“完整”；否则在标题和状态中写明范围。
3. 选择解释性控件：步骤跳转、链路切换、术语筛选和源码链接。控件只改变解释视图，不模拟未经证实的运行行为。
4. 交互状态必须有单一映射：生命周期索引、链路节点和跳转按钮共享明确的阶段字段；不同链路若阶段不一，显式保存映射，不直接复用数组下标。
5. 验证 HTML：解析脚本；检查 ID、术语 key、阶段映射和本地链接；逐个触发步骤、链路切换和完成/撤销状态。只有实际运行浏览器或截图检查后，才声称响应式或视觉验证完成。

### 解释深度与 ELI5

`how` 先提供代码定义、机制和边界。用户明确要求 ELI5 或需要类比时，按 `eli5` 的四档规则协作；类比不能改变参与者、状态转移、约束或实现边界。没有完整映射就保留直白机制摘要，不强行类比。

## 批评模式

用户明确要求架构问题、风险或改进时，先完成解释，再派独立只读评审者检查耦合、边界、可靠性、可测试性和演进成本。按以下四类归纳：

- **现在处理**：有代码证据且影响当前能力
- **考虑**：问题真实，但取舍未定
- **记录**：观察成立，优先级低
- **驳回**：证据不足、缺少上下文或只是风格偏好

批评只报告，不自动修改代码。每条意见都给出文件位置、影响和判断依据。

## 默认授权

- 直接执行：读取代码、测试和配置，派只读探索或评审，写解释草稿
- 执行后告知：把解释写入用户指定的文档
- 必须先确认：按批评结果修改架构或生产代码
