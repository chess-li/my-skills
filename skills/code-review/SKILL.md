# Code Review

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**生成者不裁决自己的工作。** 变更是否可合入，由独立评审（新鲜上下文）的裁决说了算，不由实现者的自我评估说了算；scoped 重审是修复循环内的差异自检，当前会话可做，不作裁决依据。

## 核心工作流

### 1. 派发评审者

派一个新鲜上下文的评审子代理，只给它这些：

- 目标与验收标准（来自 spec / 任务文件 / 用户要求；没有则写明本次变更的意图）
- 变更范围（相对基线的提交区间或变更文件清单）
- 代码位置
- 变更所涉 spec/design 路径（任务文件引用的章节；没有则写明无）
- 评审维度清单原文（[references/review-dimensions.md](references/review-dimensions.md)）与第 3 步分级地板

不给实现会话历史——评审独立于实现思路。评审者读代码与上述断言，不改代码。

产出要求：按维度清单逐维度给显式结论——每维度「已查 + 结论 + 证据」，无发现的维度也写已查与依据；不写没有依据的"看起来不错"。

第 2 轮起（修复循环内重派）：加带上轮发现清单与对应修复说明——评审历史不是实现思路，独立性护栏不破。本轮职责 = 先逐条验证上轮修复，再全量复看；评级按第 3 步独立锚定，不沿用上轮评级，改判引用地板条款说理由。

### 2. 评审维度

评审维度清单见 [references/review-dimensions.md](references/review-dimensions.md)——评审标准的单一信源，implement 第 6 步评审自检闸共用；维度增删只改该文件。

### 3. 发现与裁决

每条发现分级 P0（致命）/P1（严重）/P2（一般）/P3（轻微）/P4（建议）/P5（低）并附 file:line；本任务引入的死代码、测试专用物（含退化形态，界定见维度清单）、所及类型/方法上与代码矛盾的 javadoc/类注释不低于 P2；不以基线存在同类缺陷降权，基线同类实例同案列为发现。同模式缺陷归并为一条发现，全部实例位置逐个列出（同类分支/同类文件逐处 file:line），修复针对这一类——不一处一条分批报。可合入仅当无未处理的 P4 及以上发现（仅 P5 经报告不阻断）。

### 4. 处置与修复循环

按评审所处场景处置发现：

- 单纯 review 任务（用户直接发起的评审）：仅报告发现与修复建议，询问是否修复，不自动修复。
- 非单纯 review 任务（由 implement 等流程派发，如归档/合入门禁）：发现全为 P5 → 可仅报告不修复；含 P4 及以上发现 → 自动修复，不询问。

每轮修复后由当前会话对修复差异做一次 scoped 重审（自检，不派独立评审、不作裁决）——除修复对症外，逐面查修复是否引入新缺陷：测试专用物/死代码/方法体未引用的参数、删改的既有断言未等价迁回。scoped 重审无未处理发现 → 不是流程终点，调用方须立刻再派完整评审（按第 1 步「第 2 轮起」条款携带上轮发现与对应修复说明）。重审两轮仍不过 → 停下问用户。完整评审看工作分支相对基线的差异；scoped 重审只看本轮修复差异。

## 护栏

- 完整评审必须独立：评审者与被评审实现不是同一会话，实现者自审不替代；scoped 重审是修复差异自检，当前会话可做，不作可合入裁决
- 评审意见先对照代码库现实再采纳；技术上站不住的意见用理由驳回，不做表演性认同
