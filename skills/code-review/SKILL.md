# Code Review

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**生成者不裁决自己的工作。** 变更是否可合入，由独立评审（新鲜上下文）的裁决说了算，不由实现者的自我评估说了算；scoped 重审是修复循环内的差异自检，当前会话可做，不作裁决依据。

## 核心工作流

### 1. 派发评审者

派一个新鲜上下文的评审子代理，只给它这些：

- 目标与验收标准（来自 spec / 任务文件 / 用户要求；没有则写明本次变更的意图）
- 变更范围（相对基线的提交区间或变更文件清单）
- 代码位置
- 变更所涉 spec/design 路径（任务文件引用的章节；没有则写明无）

不给会话历史——评审独立于实现思路。评审者读代码与上述断言，不改代码。

### 2. 评审维度

- 规格符合度：每条验收标准/意图有对应实现，无未请求的额外功能，无未请求的历史代码删除/修复；变更所涉 spec/design 断言仍为真
- 代码质量：命名、重复、复杂度、死代码（含方法体未引用的参数）；生产代码无测试专用的方法/字段/类型/分支；无过度设计——每一层、抽象、扩展点（接口/钩子/配置项/预留位）能指出当前消费者；与同类代码的惯例一致性（结构/命名/错误处理）——实际读同类文件对比，不接受实现者自述
- 测试：验证真实行为而非 mock、边界覆盖、全部通过；断言精确度（equals 而非 contains、无空断言）、无弱化或删除断言的痕迹；注册/装配面有验证覆盖（容器加载、依赖解析、路由/配置生效）
- 生产就绪：错误处理、迁移、安全

### 3. 发现与裁决

每条发现分级 P0（致命）/P1（严重）/P2（一般）/P3（轻微）/P4（建议）/P5（低）并附 file:line；本任务引入的死代码、测试专用物、所及类型/方法上与代码矛盾的 javadoc/类注释不低于 P2——本任务导致既有生产代码退化为仅测试消费的视同测试专用物；不以基线存在同类缺陷降权，基线同类实例同案列为发现。同模式缺陷归并为一条发现，全部实例位置逐个列出（同类分支/同类文件逐处 file:line），修复针对这一类——不一处一条分批报。可合入仅当无未处理的 P4 及以上发现（仅 P5 经报告不阻断）。不写没有依据的"看起来不错"。

### 4. 处置与修复循环

按评审所处场景处置发现：

- 单纯 review 任务（用户直接发起的评审）：仅报告发现与修复建议，询问是否修复，不自动修复。
- 非单纯 review 任务（由 implement 等流程派发，如归档/合入门禁）：发现全为 P5 → 可仅报告不修复；含 P4 及以上发现 → 自动修复，不询问。

每轮修复后由当前会话对修复差异做一次 scoped 重审（自检，不派独立评审、不作裁决）。scoped 重审无未处理发现 → 不是流程终点，调用方须立刻再派完整评审。重审两轮仍不过 → 停下问用户。完整评审看工作分支相对基线的差异；scoped 重审只看本轮修复差异。

## 护栏

- 完整评审必须独立：评审者与被评审实现不是同一会话，实现者自审不替代；scoped 重审是修复差异自检，当前会话可做，不作可合入裁决
- 评审意见先对照代码库现实再采纳；技术上站不住的意见用理由驳回，不做表演性认同
