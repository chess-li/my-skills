# Spec 定义与维护

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**动手之前，把"做什么、为什么做、什么算成功"固化在纸面上，并让 spec 里的断言持续为真。** spec 是变更的第一现场：改行为，先改 spec。但 spec 刻意保持薄：只记录值得固化的行为，不是代码的镜像。

改动护栏：
- 先判断要不要 spec 再动笔：目标明确、单步可完成、不触及已有 spec 断言的，直接干活
- 信息不足 → 问用户，不猜测目标、不编造动机
- 定义层只写 what/why；技术方案属于设计阶段，不进 spec
- spec 保持薄：只写"悄悄变了会有人受损"的行为
- 断言失真时只有两条路：行为仍被需要 → 更新它；已不重要 → 删掉它
- spec 的上下文划分跟随 domains 文档；迁移跟随 domains 的变更时刻，不自行搬动

## 核心工作流

### 1. 入口判断

问三个问题：

- 启动新任务：其目标与验收标准是否已落纸面？未落且非单步可完成 → 起草新 spec
- 改动已有行为：是否改变 spec 已写过的断言？改变 → 先更新 spec
- 现场存在老标准 spec 文档（签名见迁移节）→ 提议迁移

三者皆否 → 退出流程，直接干活。

### 2. 分解与读现状

spec 的单位是限界上下文，不是需求：

- 项目已有 `DOMAINS.md` → 先读，上下文划分跟随它；没有 → 按直觉命名
- 列出本次需求触及的上下文，逐个判断：已有 spec（`docs/contexts/<限界上下文>/<限界上下文>-spec.md`）→ 更新；没有 → 新建
- 同一上下文内的多个能力合在一份文档（章节）；跨上下文引用，不复制断言
- 分与合：各部分今后按各自节奏演化 → 分；必须同进同退 → 合

### 3. 澄清访谈

写之前先列出本次需求留下的未决决策——为什么做、给谁用、做到什么边界、边缘情形怎么处理——逐条走：

- 一次一问，每问附推荐答案；多问齐发诱发敷衍
- 事实自己查（现有 spec、DOMAINS.md、代码现状），决策才问用户
- 决策都已有明确答案 → 跳过访谈直接写

### 4. 定义 what/why

写用户故事与动机。用户输入不足以回答"为什么做、给谁用"时，问，不编造。

### 5. 写验收标准

每条必须可验证：当 <谁> 做 <什么>，应观察到 <结果>。每条用户故事至少一条验收标准。写不出来 = 需求没想清楚——回澄清访谈继续问，不用模糊标准充数。

### 6. 边界自查

- spec 不含技术方案，不含 UI 拓扑（分组/方位/包含）；区域名作词汇引用，存在性可断言、结构关系不断言——拓扑是原型的探索面
- 逐条断言过筛：这个行为悄悄变了，会有人受损吗？不会 → 删掉该断言
- 新建：每条用户故事都有验收标准；更新：新旧断言不矛盾

### 7. 落盘

- 新建写入 `docs/contexts/<限界上下文>/<限界上下文>-spec.md`（项目已有 spec 存放约定则跟随；属本体系被超越的旧布局除外——见迁移节），模板如下
- 更新在原文件就地修改断言，并追加一行变更历史
- 单文件大到难以维护时，在同目录按能力拆文件，命名 `<限界上下文>-spec-<能力名>.md`
- 语言跟随项目文档语言；无文档则跟随用户输入语言
- git 仓库：落盘后单独提交本次 spec 变更，不与后续代码变更混合
- 完成后：本会话目标含实现该改动 → 接续 <use-skill>implement</use-skill>（design 就绪由其入口自判）；纯文档变更 → 告知用户 spec 已就绪

**文件模板**：

```markdown
# <上下文名>

## <能力名>

### 动机
为什么存在，解决什么问题

### 用户故事
- 作为 <角色>，我想要 <能力>，以便 <价值>

### 验收标准
- 当 <谁> 做 <什么>，应观察到 <结果>

## 变更历史
- YYYY-MM-DD 新建 / 变更 <什么>
```

## 冷启动（项目还没有 docs/ 结构时）

不要一次建成体系：第一份 spec 建起第一个 `docs/contexts/<限界上下文>/` 目录即可，不建索引；文件多到难找入口时再补。上下文划分不追求一步识别正确，直觉命名，domains 成熟后对齐改名。

## 迁移（老标准 → 现行约定）

检测到老标准文档即提议，用户同意后执行，不静默迁移。

**老标准签名**（均为本体系被超越的旧约定）：

- 布局：`docs/requirements/`、`docs/specs/` 下的需求或规格文档；`docs/<上下文>/` 直挂（现行：`docs/contexts/<上下文>/`）
- 结构：缺模板四件（动机/用户故事/验收标准/变更历史），或混有技术方案、UI 拓扑
- 项目自成一体的他类布局不算老标准——不擅动，仅报告

**提议**：列出迁移清单——文件、布局搬法、结构改法、引用同步点（DOMAINS.md 索引、文档互引、AGENTS.md、任务文件）——确认后执行。

**执行**：

- 布局用 git mv 以上下文目录为单位搬迁（同目录 design/domains 随同，内容归各自 skill 管辖不改），并同步全部引用
- 结构按模板改写；验收标准写不出 → 回澄清访谈（第 3 步）
- 迁移单独提交（docs-only），不与代码变更混合；变更历史追加迁移记录

## 完整示例（一次跨上下文需求）

- **现场**：用户说"想支持企业账户下单"
- **入口判断**：新能力，未落纸面 → 需要 spec
- **分解**：触及账户、订单、计费三个上下文。账户新增企业类型 → 更新 `docs/contexts/账户/账户-spec.md`；"企业下单"作为订单能力的新章节，引用账户 spec → 更新 `docs/contexts/订单/订单-spec.md`；计费规则随之变化 → 更新 `docs/contexts/计费/计费-spec.md`
- **澄清**：列出未决决策逐条问，每问附推荐（企业账户需要审批吗？→ 推荐要，走现有审批流；计费怎么合并？→ 推荐并入主账单）
- **定义**：写用户故事与验收标准
- **自查**：删掉一条"页面展示企业标识"——悄悄变了没人受损，不值得守护
- **落盘**：三份文件就地修改、追加变更历史，告知用户可进入设计
