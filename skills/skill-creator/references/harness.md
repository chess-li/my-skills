# 观测基础设施：三层架构

观察-证明-优化是控制回路，skill 只是它的策略宿主。体系按**执行者**分三层，不按概念切 skill：

- **机制层（harness）**：证据日志等确定性捕获设施——负责捕获。skill 给不了确定性执行、持久状态、定时触发，捕获不该拜托模型"记得做"
- **策略层（skill-creator 迭代分路）**：证据判据、取证流程、升格闸、四步工作流——判断的载体
- **原理层（design-principles.md）**：创建与审查共用的设计原理

## 机制层现状与重建判据

当前机制层只有 `skill-证据日志.md`（工作区根目录，追加式 markdown：观察名单 / 返工事件 / 升格移出 / 冻结状态），agent 维护；事件只记机械事实，语义归因在取证时完成。

hook 观测（捕获脚本 + 用户级 hooks.json + 周心跳）2026-08-06 落地、2026-08-26 拆除：部署 20 天零真实捕获（安装静默丢失，自建的心跳防御同失，无人察觉），用户裁定无实际用处。教训：装得上 ≠ 活得下去——机制层建设同样过证据闸。

再建捕获机制的拉动条件：出现「需要某现场记录而它不存在」的真实取证缺口；建成后首周零产出即拆。

## 拆分判据（防止把层次误拆成 skill）

新概念先问归属层，不问"要不要新 skill"。捕获不是 skill（没有模型触发场景）；创建与迭代由 skill-creator + 原理层值守；仅当某职责长出独立触发场景（如定期巡检证据日志的审计），才允许拆出独立 skill——且优先 user-invoked 或定时触发，不付常驻成本。
