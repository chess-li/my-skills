## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**可预测性**——每次运行走同样的过程，而不是每次产出同样的文本。

- **创建期**：触发、上下文、结构三处不欠债；不造无真实语料的测试集
- **迭代期**：复发模式才立规则；改动附带证据；无对比不合并；测试集随真实使用/返工建成

护栏：
- 先定调用方式再动笔；仅手动调用的 skill 不写 description
- description 写本质能力与判别边界，不枚举用户说法
- 正文每句话过审计四问；模型已知的一律不写
- 无证据的想法进观察名单，不落地；冻结 skill 只接受修复
- 测试输入必须来自真实使用（含创建该 skill 的需求原话以外的后续场景）；无真实语料不建集、不生成假用例

## 分路

| 现场 | 走 |
|---|---|
| 目标 skill 不存在 / 从零起草 | **创建工作流** |
| 已有 skill 要改、审、补测试集 | **迭代审查工作流** |
| 用户说"优化一下"但无失败证据 | 可审查，产出分级：有证据→修；理论项→观察名单 |

设计原理（触发、差值、授权、workflow、措辞）→ 读 [references/design-principles.md](references/design-principles.md)；不可得时用下方审计四问兜底。

**审计四问**（创建写正文与迭代改正文共用）：

1. 没有这句，模型也会做对吗？ → 删
2. 模型知道但会忘？ → 压成清单短句
3. 模型不知道？ → 写成明确知识
4. 必须每次精确一致？ → 挪进 scripts

## 创建工作流

四步，顺序不可跳过。测试集不在创建期交付——无使用现场的语料只会产生假用例；首次真实返工或用户提供语料时走「冷启动」补建（见迭代分路）。

### 1. 定调用方式

- 需 agent 自动触发或被其他 skill 调用 → model-invoked，保留 description
- 仅人手动调用 → user-invoked，去掉 description；手动 skill 多到记不住时用 router skill 做目录

### 2. 写 description（model-invoked 时）

结构 = 本质能力 + 类别级锚点（≤4 个代表例，可含管辖产物字面名）+ 负向边界（"不用于 X，那是 Y skill 的事"）。自查：每句贡献触发判别？在枚举说法？与相邻 skill 划界了？

### 3. 按差值原则写正文

逐段过审计四问。结构：workflow 一条主干 ≤7 步，锚定产物不锚定状态；授权分三档，常见决策点写死默认值。

### 4. 选词过双闸

闸一·招募共识：优先模型/行业/社区/大众已有概念，自造词是最后手段且定义必须显式写入。闸二·招来的干净：联想恰好等于所需含义。禁令配正向目标；每个含义单一信源。

交付即提交（规则见迭代第 4 步）。

## 迭代审查工作流

四步，顺序不可跳过：

### 1. 诊断到机制层

完成物：病灶层 + 机制一句话（非表面症状）。

| 症状 | 病灶层 | 错误修法 |
|---|---|---|
| 不触发 / 过触发 | description 判别逻辑 | 改正文、堆关键词 |
| 频繁要求确认 | 授权与默认值缺失 | 删"请确认"话术 |
| 上下文臃肿 | 冗余与自由度错配 | 直接拆分 |
| workflow 越改越臃肿 | 状态写进文本 | 继续加状态转移 |
| 移植后过触发/异物感 | 誊写文本而非机制 | 事后清触发词 |
| 越优化问题越多 | 无证据改动循环 | 继续"优化" |
| 脚本找不到 / 跑错同名脚本 | 路径锚点缺失 | 在每条命令里硬编码绝对路径 |

### 2. 证据闸与改动意图

完成物：模式一句话 + 证据引用（返工日期或测试失败）+ 破坏面预判；理论项则观察名单条目（无正文 diff）。

**无证据，不动手。** 证据 = 一次真实返工，或一条测试失败。

- 阻断性项（有失败证据）→ 立即修
- 理论性项（仅"不够完善"）→ 观察名单，等真实使用

**冻结**：冒烟集通过 + 近约 10 次使用零返工（无日志时以用户确认为准）。冻结 skill 只接受修复，不接受优化。

写不出模式句 → 仍在修症状，回第 1 步。

### 3. 执行修改

完成物：目标文件 diff，或明确「无改动」。

优先级默认：description 措辞 > 删冗余 > 压缩措辞 > 结构调整。加法先过审计四问。从他库提取 →「移植纪律」。补测试集 → testing-guide。

### 4. 回归对比与减法审查

完成物：新旧对比结论 + 冒烟/失败输入结果；每加对应可观察的删或「无可删」。

改动落盘即提交：一个逻辑改动一个提交（证据日志追加与正文改动同提交），信息一句话带依据（返工日期/用户指令）；目标不在 git 仓库则跳过，不提议 init。

- 必须新旧对比，无对比不合并；尚无测试集时至少重跑触发改动的失败输入，并按「冷启动」补冒烟集
- 每加一条规则，检查是否有因此可删的旧规则
- 每 5–10 轮迭代整体重构，把补丁压回干净结构

## 冷启动（无日志、无测试集时）

1. 投诉即第一份证据，已满足证据闸
2. 从投诉与历史对话摘 3–5 条输入建冒烟集，预置固定目录
3. 回归：失败用例 + 冒烟集；全量等测试集长大
4. 证据日志从一个追加式 markdown 起步（见「证据体系」）；hook 等被咬过再建（[references/harness.md](references/harness.md)）

## 证据体系

证据强度按粘性配比：

- **可逆采纳**（进参考文件）：社区经验可直接采用
- **升格进正文**：须用户一字批准；规则进得来很少出得去
- **升格由真实事故拉动**：本可防止该事故的参考原则 → 升正文；长期与事故无关 → 移出候选

**证据日志**（工作区固定 `skill-证据日志.md`，agent 追加、执行后告知；升格同须用户一字批准）四区：

1. 观察名单：理论项 + 来源 + 待验证缺口
2. 返工事件：日期 | skill | 症状 | 疑似病灶层——升格的唯一合法证据源
3. 升格 / 移出：内容 + 依据，引用返工日期
4. 冻结状态：skill | 日期与判据

观测分工：用户只看结果；过程记录与取证是 agent 的活。基础设施见 harness.md。

## 移植纪律

1. **先诊断，后提取**：一句话声明目标 skill 的具体缺口；写不出不提取
2. **找机制，不找段落**：提取判别边界/产物断言/默认值等机制本身
3. **翻译，不誊写**：在目标语境重新实例化；源专有名词、触发词、路径、工具名全部重写
4. **合入后过两道检查**：审计四问 + 触发测试集（防过触发）

## AI 协作的四个已知偏差

1. **加法偏好** → 先要求删除方案
2. **教科书化** → 测试输入模仿真实语料，非需求文档腔
3. **拆分偏好** → 先走完删减与压缩，拆分排最后
4. **形式化偏好** → workflow 锚定产物，不写状态机外观

## 交付判据

**创建：**
- SKILL.md 存在，name 与目录名一致，description ≤1024 字符（model-invoked）或无 description（user-invoked）
- 正文每句可归入审计四问某一档
- 未附假语料测试集（测试集留待真实使用后按冷启动/testing-guide 补）

**迭代：**
- 改动附带证据引用；有新旧对比结论
- 理论项只在观察名单，未进正文
- 每加有对应可观察的删或明确"无可删"
- 补建或扩展测试集时，输入均有真实来源标注
