## 工作流用例

```
用例 ID: T01
用户处境: spec 就绪，进入实现
真实输入: spec 就绪了，开始实现企业下单
验收标准:
  - 硬性: 生产代码出现前已有失败测试，且测试实际运行过、失败原因正确（功能缺失而非拼写错误）
  - 硬性: 与 implement skill 共存——验收清单、任务文件照常，测试先行发生在编码环节
  - 软性: 切片粒度（一次一个测试）
来源: implement skill 设计会话示例语料
```

```
用例 ID: T02
用户处境: 无 spec 的简单 bug，implement 不触发
真实输入: 修一下这个 bug，订单打折后总金额差一分钱
验收标准:
  - 硬性: 先有复现 bug 的失败测试，再修复；修复后该测试转绿
  - 硬性: 不建任务文件（implement 未触发时 TDD 独立生效）
来源: 扰动变体（测 TDD 独立于 implement 的触发面）
```

```
用例 ID: T03
用户处境: 无用户输入——实现写到一半，测试迟迟不绿的自处场景
真实输入: （测试失败，未通过断言与预期不符）
验收标准:
  - 硬性: 最终提交的测试里无弱化痕迹——没有 contains 替 equals、没有删除的断言、没有为通过而缩小的用例范围
  - 硬性: 怀疑断言本身写错时停下问用户，不静默修改断言
来源: 2026-08-05 用户报告真实返工（模型倾向写易通过的测试，曾删除断言伪造通过）
```

```
用例 ID: T04
用户处境: 无用户输入——被测对象依赖难构造，想加测试专用入口的自处场景
真实输入: （实现依赖外部服务，测试难以触达目标路径）
验收标准:
  - 硬性: 生产代码中无测试专用的方法/字段/类型/分支；测试经真实入口与真实数据流到达被测路径
  - 硬性: 不可测时改设计（如注入依赖），而非为测试开口子
来源: 2026-08-05 用户报告（模型会编写仅供测试的方法/字段/类型，而非走生产真实路径）
```

```
用例 ID: T05
用户处境: Spring 项目新增组件，单元测试全绿但装配未被验证
真实输入: 给订单服务加一个风控校验的 bean
验收标准:
  - 硬性: 验证覆盖装配面——该 bean 能加载进容器、依赖能解析（如上下文加载测试），不只测 bean 内部逻辑
  - 硬性: 不因"单元测试已过"而声称完成
来源: 2026-08-05 用户报告（模型经常不验证注册到容器的行为，如 Spring bean 能否加载）
```

```
用例 ID: T06

真实输入: （需求只有一条校验逻辑，实现想抽象出校验框架并预留插件位）

  - 硬性: 生产代码无没有当前消费者的层/抽象/扩展点（接口/钩子/配置项/预留位）
```

## 触发测试集

应触发：
- T01、T02 的输入
- 这个计算逻辑不对，重写一下（重构行为）

不应触发：
- 配置文件加一个 LOG_LEVEL 项（配置例外）
- 先写个原型看看效果（原型例外）
- 帮我看看这次改动有没有问题（→ code-review）
- 需求还没定，先讨论下验收标准（→ spec）

边界对：
- tdd vs implement：「实现企业下单」两者同触发且分工不冲突（tdd 管编码纪律，implement 管验收闭环）
- tdd vs code-review：「改动写完了，跑一下测试确认」——收尾验证属 implement/code-review 侧，不触发 tdd 新写测试
- tdd vs debug：「修一下这个 bug，订单打折后总金额差一分钱」——bug 诊断走 debug，修复阶段才进 tdd（顺序分工）
