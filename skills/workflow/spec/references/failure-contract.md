# 失败契约参考

## 读取条件

本能力包含外部调用、异步任务、超时、重试、队列、复制或派生数据、迁移、容量边界，或可能出现“请求结果未知”时读取本文件。没有这些边界时跳过，不把本表当作所有能力的固定清单。

本文件只提供字段和检查问题。`spec` 负责用户可观察行为与验收标准；`design` 负责技术决策与取舍；`code-review` 负责对照实现和交付证据。它不替代任何一个消费者的断言。

## 最小字段

按一个外部边界、异步流程或数据副本填写一行。字段不适用时写“不适用”和原因，不能留空。

| 字段 | 要回答的问题 | 主要落点 |
| --- | --- | --- |
| 边界与责任 | 谁调用谁？哪一侧拥有这次操作的语义？ | spec / design |
| Source of truth | 哪份状态是权威？哪些是缓存、日志、投影或其他派生物？ | spec / design |
| 成功阶段 | 接收、持久化、应用、可见、耐久分别何时成立？ | spec |
| 可见性与一致性 | 允许多旧的读？冲突怎样发现和处置？ | spec / design |
| 超时与取消 | 等待多久？超时后调用方和被调用方各自怎样结束？ | spec / design |
| 重试资格 | 哪些错误可重试？重试次数、总时间、退避和抖动如何受限？ | spec / design |
| 重复与重放 | 重复请求、消息重放或乱序会发生什么？用幂等键、去重或恢复契约怎样保护副作用？ | spec / design |
| 容量与隔离 | 队列、连接、线程、批量和并发的上限是什么？过载时怎样背压、隔离或降级？ | design |
| 恢复与修复 | 部分成功、失败迁移、失联副本或派生数据损坏怎样重建、对账或回滚？ | spec / design |
| 诊断信号 | 用户是否能看到状态、错误或查询结果？内部怎样关联一次调用、重试、超时、冲突和修复，失败证据写在哪里？ | spec（仅用户可见结果） / design / code-review |
| 演进兼容 | schema、事件、配置或协议怎样向前/向后兼容？旧数据怎样处理？ | spec / design |

## 使用顺序

1. 先在 spec 中写用户可观察的成功、失败、重复、超时和恢复结果。
2. 再在 design 中写实现这些结果所需的边界、预算、隔离和取舍。
3. 对每个重试或重放路径说明副作用保护；没有保护时不能默认重试。
4. 对每个派生数据说明传播、滞后、诊断和重建路径；没有修复路径时标为未决。
5. 对“未知成功”写对账或查询结果的恢复方式，不能把客户端超时直接当作失败。
6. 在 code-review 中按适用字段核对 spec、design、代码、配置和验证输出；无法核对时写“未验证”。诊断的内部实现不要求复制进 spec。

## 固定边界

- 本参考不规定具体秒数、次数、容量或一致性等级。数值必须来自项目约束、测量或用户裁定。
- 不把“最多一次”“恰好一次”当作默认实现语义。必须写出副作用、重试和恢复证据。
- 不把缓存、队列、事件、索引、搜索副本或物化视图当作权威状态，除非 spec/design 明确声明所有权。
- 不因本表出现技术字段就把它们写进 spec 的实现方案；spec 只保留用户可观察的结果。
