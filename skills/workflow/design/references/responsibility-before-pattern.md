# 责任先于模式

## 读取条件

技术决策开始使用或比较分层、事务、仓储、映射、网关、服务层、事件、适配器、端口、聚合或其他结构模式时读取本文件。只改局部实现细节、且不产生值得固化的技术决策时跳过。

本文件只约束设计决策的顺序。`spec` 负责 what/why 和用户可观察结果；`domains` 负责上下文语言；`design` 负责 how、边界和取舍。

## 决策顺序

1. 写清本次能力、上下文和必须保留的用户可观察结果，引用 spec，不复制它。
2. 写清责任归属：谁拥有业务规则、谁编排用例、谁访问数据、谁负责传输或外部集成。
3. 写清不变量、事务/一致性边界、失败语义和跨边界的翻译责任；跨上下文时先确认本地术语和关系，不共享外部模型作为默认方案。
4. 说明边界解决了什么耦合、变更扩散、隔离或测试问题，并指出当前消费者和装配位置。
5. 在责任和约束稳定后选择最轻的可行形状；模式名是结果，不是问题的起点。简单流程先验证是否真的需要额外层、接口或事务仪式。
6. 记录被放弃的选项和原因；如果选项来自社区或 subagent，标出已核对、项目约定和未复核部分。
7. 用一个真实调用或数据流检查边界：没有当前消费者、只转发、只增加名称，或让远程调用隐藏在长事务中的结构不得落盘为默认方案。

## 评审问题

- 每一层是否减少耦合或澄清责任？不能回答时删除该层。
- 事务由谁拥有？远程调用、重试和失败恢复是否仍可观察？
- 聚合或其他一致性边界是否只承载需要立即一致的不变量？跨边界是否使用身份和明确翻译？
- 模式是否服务于当前约束，而不是把简单 CRUD 或通用流程升级成仪式？
- 设计是否引入了没有消费者的接口、端口、配置项或扩展点？

## 来源和本地证据

本参考翻译了 `agent-rules-books` 中 Patterns of Enterprise Application Architecture、DDD、DDD Distilled 和 Implementing DDD 的相容机制；它保留本仓库对模式冲突的限制，不创建书名 skill，也不预建领域词条。建立它的本地证据包括：2026-09-26 三个设计选项在先行社区调研后全部重写，说明先列模式方案会固化错误前提；此前设计评审也发现端口、命名和跨边界决策必须记录责任与取舍。有效性仍需在后续真实设计返工中观察。
