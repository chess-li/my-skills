# writing 冒烟集

每次改动后必跑。断言指向交付物价值，不指向步骤服从。
当前为创建期拟真语料；进入使用期后按 testing-guide 用真实语料逐条替换。

```
用例 ID: T01
用户处境: 刚做完一个命令行天气查询小工具,准备发到 GitHub
真实输入: 帮我写个 README,项目是个命令行查天气的工具,输入城市名出结果
验收标准:
  - 硬性: 无营销形容词(强大/好用/seamless);每个标题承载信息(无"概述")
  - 硬性: 全文事实不超出对话与代码库可查证范围,编造功能或环境要求即失败
  - 硬性: 无客套结尾
  - 软性: 用户拿到无需调整即可发布
来源: 创建期拟真语料
```

```
用例 ID: T02(历史翻车型:润色丢事实)
用户处境: 写给运维的变更说明太口语,要转成正式通知
真实输入: 这段帮我润色下 看着有点乱:"昨晚10点左右缓存集群挂了一台,重启之后好了,但是今天上午又有点慢,我们怀疑是内存的问题,先观察下"
验收标准:
  - 硬性: 时间、事件、判断(怀疑内存)零改动零丢失;程度守恒——"有点慢"不得写成"严重"级表述
  - 硬性: 不添加原文没有的事实(如编造根因结论)
  - 软性: 长句已拆,语句通顺
来源: 创建期拟真语料;润色丢事实、拔高程度是此类任务最高发翻车
```

```
用例 ID: T03
用户处境: 修完 login timeout 的 bug,要提交 PR
真实输入: write a short PR description: fixes the login timeout bug, root cause was a missing keepalive
验收标准:
  - 硬性: 首句即结论(修复了什么);无 em-dash;无 delve/leverage 类词
  - 硬性: 无 "I hope this helps" 类结尾
  - 软性: 紧凑,不超过必要长度
来源: 创建期拟真语料
```

```
用例 ID: T04
用户处境: 团队中文沟通,技术词保留英文,要给项目补部署说明
真实输入: 在 docs 里写个部署说明,用 Docker 部署,要调 API 密钥那块也写上
验收标准:
  - 硬性: 中文标点全角;中文与英文/数字之间加半角空格
  - 硬性: 无翻译腔(无冗余"作为",被动不泛滥)
  - 硬性: "API 密钥"一词到底,不在"API 密钥/接口密钥/密钥"间换
  - 软性: 标题承载信息
来源: 创建期拟真语料
```

```
用例 ID: T05(口语、半截)
用户处境: 会上随手记的要点要变成发给全组的公告
真实输入: 把这几点写成公告:1.下周三停服维护2小时 2.提前备份数据 3.有问题找值班同学,哦对时间还没最终定
验收标准:
  - 硬性: 时间未定这一不确定状态明确保留(写"待确认"),不得写成确定时间
  - 硬性: 三条信息零丢失
  - 软性: 公告草稿可直接发送
来源: 创建期拟真语料
```
