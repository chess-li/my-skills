# Spec 实现

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**目标与验收标准已在纸面，实现的职责是让每条验收标准通过，并让执行状态随时可被任何接手者续写。** 完成的定义只有"验收标准通过"，不是"代码写完了"。

实现护栏：
- 验收强制：每条验收标准对应一个验证手段，验一条记一条；未验证的验收标准 = 未完成
- 任务拆分留在会话内，不落盘；任务文件只承载目标、验收清单、验证状态，是执行的唯一交接介质
- 偏差路由：触及 spec 断言或 ARCHITECTURE.md → 停下问用户；只触及 BC design → 按 <use-skill>design</use-skill> 先改文件再实现
- 范围与整洁：改动限于验收标准所需，本任务产出不留死代码、注释掉的代码、未使用的导入；顺手发现的范围外问题记入任务文件「范围外问题」，不顺带修复或删除
- 验证状态实时落盘，不依赖会话记忆——接手者可能是另一个模型
- 全部验收通过 → 任务文件移入 archive，不滞留 `docs/tasks/`
- git 仓库：worktree 内只改代码与任务文件，spec/design 修正一律回主 checkout；merge 基线分支只两处——取回修正、归档前

## 核心工作流

### 1. 入口判断

- 新实现：有就绪的 spec？ → 第 2 步
  - design 就绪：本次改动触及的值得固化的 how 问题未落定（BC design 或 ARCHITECTURE.md）→ 先走 <use-skill>design</use-skill> 落定再回来；改动不产生值得固化的决策 → 空满足
- 续写：`docs/tasks/` 下有未归档的任务文件？ → 读它，按"当前位置"恢复执行

  ```bash
  # invocation optional
  git worktree list   # git 仓库：有任务 worktree 时，进行中的任务文件在其内
  ```
- 皆否 → 退出流程，直接干活

### 2. 建任务文件

写入 `docs/tasks/<需求名>.md`（项目已有任务存放约定则跟随），模板见下：

- 逐条抄录 spec 的验收标准，为每条预填验证手段，优先级：可落成测试 → 该测试；其他可自动化的命令 → 命令；皆否 → 人工确认步骤
- 写不出验证手段 = 验收标准不可执行——回 <use-skill>spec</use-skill> 修正，不用模糊条目充数
- 跨上下文需求共用一份任务文件，目标分别引用各 spec
- git 仓库：从基线分支（当前检出的分支）建 worktree：默认 `<项目根目录>/.worktrees/<需求名>`（首次把 `.worktrees/` 写入 `.gitignore`），分支名 = 需求名，基线分支与起点 commit（建任务时基线顶端）记入任务文件；此后实现在 worktree 内进行

### 3. 拆分与执行

会话内拆成步骤逐个执行。粒度自定，唯一约束是覆盖全部验收标准。写生产代码遵循 <use-skill>tdd</use-skill>（测试先行）。

### 4. 验证与记录

每完成一条验收标准：执行其验证手段（无法自动化 → 请用户确认），把结果写入任务文件，更新"当前位置"，随后提交（git 仓库，含任务文件）。失败 → 修复重验；重验仍失败且判断是标准本身的问题 → 第 5 步。

### 5. 偏差路由

- 验收标准互相矛盾、按字面不可实现、边缘情形推出荒谬 → 停下，向用户陈述偏差，裁定后走 <use-skill>spec</use-skill> 更新，再回来
- 发现 design 决策不适用：只触及本 BC design → 先改 `docs/contexts/<限界上下文>/<限界上下文>-design.md` 再实现；触及 ARCHITECTURE.md → 停下问用户
- git 仓库：上述 spec/design 修正回主 checkout 落盘（提交到基线分支），worktree merge 基线分支取回修正后继续

### 6. 完成与归档

- 全部验收标准通过 → worktree 内先 merge 基线分支；带入新变更 → 重跑全部验证手段
- 验证仍通过 → 跑项目的 lint/typecheck（如有）：本次改动引入的新失败 = 未完成，回第 4 步修复；既有的范围外失败 → 记入「范围外问题」，不顺带修复。过后派 <use-skill>code-review</use-skill> 评审任务分支变更（变更范围 = 任务文件的提交区间），裁决可合入 → 归档；有 Critical/Important 发现 → 修复后回第 4 步
- 归档：补记终点 commit（任务分支顶端），任务文件移入 `docs/tasks/archive/` 并提交，任务分支合入任务文件记录的基线分支（项目走 PR 流程则改开 PR），移除 worktree，告知用户并附各条验证结果
- 中断（会话结束、换人）无需额外操作：状态已逐条落盘，任务文件即交接介质

**任务文件模板**：

```markdown
# <需求名> 任务文件

## 目标
<一句话>，满足 spec：docs/contexts/<限界上下文>/<限界上下文>-spec.md §<能力名>
基线分支：<建任务时检出的分支>（合并目标；非 git 项目省略本行）
提交区间：<建任务时基线顶端 commit>..<归档时任务分支顶端 commit>（终点归档时补记；非 git 项目省略本行）

## 验收清单
- [ ] <验收标准（抄自 spec）> —— 验证手段：<命令 / 人工确认步骤>
- [x] <验收标准> —— 已验证：<命令>，结果：<一句话摘要>（YYYY-MM-DD）

## 当前位置
<下一步要做的事>

## 变更历史
- YYYY-MM-DD 创建 / <变更什么>

## 范围外问题（顺手发现，本次不修）
- <问题 + 位置>
```

## 归档合并

同一 spec 的任务归档累积多份，用户发起合并时：

- 逐条与 spec、design、现有代码核对：已完成条目已过期 → 安全删除；待办已被其他方案替代 → 安全删除。按各归档的提交区间定位任务改动；区间因 squash 悬空时以现存代码为据
- 汇总按 spec 当前断言组织，验证证据指向现存测试；产出是反映已完成/未完成的当前状态视图，不是按任务历史直接合并的流水
- 删除项记入「核对删除备查」节（条目 + 依据）；原始任务文件由 git 历史保留，不另存副本

## 冷启动

项目没有 `docs/tasks/` 时，随第一份任务文件创建；`archive/` 首次归档时创建。不预建空目录、不建索引。

## 完整示例（一次带偏差的实现）

- **现场**：用户说"spec 就绪了，开始实现企业下单"
- **入口判断**：`docs/contexts/订单/订单-spec.md` 有"企业下单"章节，无任务文件 → 建 `docs/tasks/企业下单.md`，抄录三条验收标准并预填验证手段（两条跑命令，一条请用户人工确认审批流）
- **执行**：会话内拆成四步；实现中发现 design 的订单状态流转未覆盖审批分支 → 只触及订单上下文：先改 `docs/contexts/订单/订单-design.md` 再实现
- **验证**：两条命令验证通过并落盘；一条边缘标准（审批拒绝时订单自动取消）按字面不可实现——spec 未定义退款去向 → 停下问用户，spec 更新后继续
- **归档**：全部通过，任务文件移入 `docs/tasks/archive/`，告知用户三条验证结果
