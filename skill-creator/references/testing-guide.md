# Skill 测试集建设指南

**时机**：测试集在使用期/首次返工时建（见 SKILL.md 冷启动），不在从零创建 skill 时顺手编造。无真实语料 → 不建集，记欠账等语料到场。

## 目录

1. 语料采集：从真实使用中来
2. 三层覆盖结构
3. 用例模板
4. 触发测试集（独立子集）
5. 回归对比流程

7. 验证的注意力经济学：结果优先于过程
8. 防过拟合策略
9. 让 AI 协助时的正确用法

## 1. 语料采集：从真实使用中来

测试输入的最优来源是用户实际说过的话，**原样摘录**：

- 翻历史对话，截取真实请求——包括错别字、口语、半截话、"不对重来"式追改
- 失败案例必须入库（它们是历史上打补丁的动机，防复发）
- 5 条真实语料胜过 20 条生成语料；**0 条真实时不生成凑数**
- 之后每次真实使用中遇到新说法，随手补进语料库

总量建议 8–15 条：足够覆盖，又不会因为跑一遍太耗时而被弃用。创建 skill 的那条需求原话可以作种子，但不构成"已有测试集"——还要等后续真实场景。

## 2. 三层覆盖结构

**难度分层**：
- 简单任务（约一半）：验证核心流程不退化
- 中等任务（约三成）：常规变体，验证泛化
- 困难/边缘任务（约两成）：历史失败、极端参数、模糊表述——回归测试重点

**类型分层**：skill 支持的每类任务至少 2 条。

**变体分层**：同一意图换几种说法，测触发健壮性。

按真实使用频率加权，不均匀撒网。

## 3. 用例模板

```
用例 ID: T03
用户处境: 月底最后一天，需要把三份原始数据合并发给财务
真实输入: （原样摘录，含口语与省略）
验收标准:
  - 硬性: 合并无遗漏无重复；日期格式与财务模板一致
  - 硬性: 用户拿到后无需调整即可发送
  - 软性: 排版清晰度
来源: 2025-12 曾因漏 sheet 返工
```

关键规则：

- **断言针对交付物价值，而非步骤服从**。写"用户拿到可直接使用"，不写"是否执行了规定的第 3 步"。过程约束确有必要时单独标注为硬性项，但必须搭配一条结果断言。
- **持有 skill 不知道的秘密**：部分验收标准只存在于测试集、不写进 SKILL.md。两边都有的检查项只是复读机，测不出盲区。
- **绑定用户处境与来源**：强制测试锚定真实价值，也引导后续 AI 协助扩展时走向正确方向。

## 4. 触发测试集（独立子集）

把每条用例的输入话术单独抽出，加上反向样本，组成触发测试集：

- 应触发的输入一组
- 不应触发的输入一组（邻近 skill 的任务、形似但无关的请求）
- 每对相邻 skill 各加 1–2 条踩在边界上的输入

每次修改 description 后全量过一遍，两端（欠触发/过触发）都要测。

## 5. 回归对比流程

1. 用当前版本 skill 跑完全部用例，输出存档作为 baseline
2. 修改后重跑全部用例
3. 逐条记录：变好 / 变差 / 不变
4. 事先定好合并门槛，例如：不允许任何硬性指标退化；软性指标允许个别波动但整体不变差

执行细节：

- 隔离变量：同输入、同模型、干净对话环境，否则分不清差异来自改动还是模型随机性
- 重要用例跑 2–3 次取多数结果
- 记录用简表：用例 ID、版本、通过/失败、备注

## 6. 运行成本控制

测试集最常见的死因不是设计缺陷，而是运行太耗时导致被弃用。原则：**一个每次都跑的小测试集，价值远超一个被放弃的完美测试集。**

**分层运行：冒烟集 + 全量集**

- 冒烟集（3–5 条）：核心流程各一条 + 历史翻车最狠的一条。每次改动后必跑。大部分退化会在核心流程显形，冒烟集可拦住多数问题。
- 全量集：只在里程碑时跑——累计约 5 次改动后，或一次大重构后。
- 回归测试的目标不是"每次改动证明全对"，而是"退化发生后能在合理延迟内被发现"。

**只跑受影响子集**

建集时给每条用例标注覆盖的能力域（触发、格式、合并逻辑……）。改 description 只跑触发子集，改某段逻辑只跑相关用例。全量回归因此变得罕见。

**压缩人工环节**（运行时间的大头常是对比劳动，不是 agent 执行）：

- 硬性断言脚本化：文件可打开、sheet 数、字段齐全、无报错——自动查，只人工看失败项
- 与 baseline 做 diff，只审差异点，不重读全文
- 用例的输入文件与话术预置在固定目录，跑时直接取用

**触发测试集单独高频跑**

触发判断无需 agent 完整执行任务——看干净会话里加载了哪个 skill 即可，一条几秒钟。它与工作流测试不混在一个运行单元。

**时间硬预算**

冒烟集 15 分钟内跑完。超时说明该砍用例，不是延长时间——超时硬跑会滑向拖延、跳过、最终弃用。

## 7. 验证的注意力经济学：结果优先于过程

用户的注意力是整个验证体系里最贵的资源。验证方案必须建在用户**本来就关心的信号**（结果能不能用）上，而不是容易观察的信号（触发了没有、调用差异）上。依赖用户持续关注过程信号的体系注定被弃用。

**核心认知：过程信号是诊断工具，不是常备监控对象。**

- 结果好而过程"错"（如 skill 未触发但任务完成良好）：无需警觉，只说明该 skill 在这类任务上无增量价值
- 过程全对而结果要返工：这才是问题
- 结果信号零成本采集——被迫返工的那一刻用户天然知道，挫败感自动上报；调用差异不会自动上报

**返工触发式诊断（默认验证结构）：**

1. 平时不盯任何过程指标，正常使用，只看结果；顺手即默认健康
2. 过程数据被动记录：让 agent 每次任务后自动追加一行日志（用了哪个 skill、是否中途返工）——agent 做自己的 QA，不占用用户注意力。此要求可直接写进被测 skill
3. 只在返工发生时激活诊断：调出日志定位——未触发？触发了未读正文？读了但规则缺失？过程信号只在绑定真实结果失败时才有阅读价值
4. 版本对比类问题（如两版 description 孰优）同样用结果裁决：触发用例由 agent 批量跑并自动汇总，用户只验收结论，不旁观过程

**分工原则：** 用户保留"结果验收官"角色（只有用户能判断"愿不愿用"）；过程监控一律自动化或降级为按需调取的诊断材料。

## 8. 防过拟合策略

反复根据测试集调 skill，最终会对这批用例完美、对新任务翻车。对策：

- 每隔几轮优化，从最近真实任务中替换 20–30% 用例
- 留一组"验证集"：不参与日常优化决策，只在里程碑时测一次，检验泛化是否真在涨
- 警惕"只为过某条用例而加的规则"：先判断它是通用规律还是特判

## 9. 让 AI 协助时的正确用法

**定位：AI 做扰动，不做创作。** 真实语料做种子，AI 围绕种子做可控变异：

- 换说法：同一意图的 3 种口语化表达
- 删信息：逐个去掉参数，测默认值与追问行为
- 加噪声：混入无关上下文、错别字、语音输入式断句
- 推边界：一半需求在 skill 内、一半在外

**必须从零生成时**，给人设和反例压住教科书腔：

> 生成 10 条用户输入。要求：每条不超过一句话；至少 3 条缺少关键参数；至少 2 条口语化到近乎随意；至少 2 条包含前序对话引用。以下是过去的真实输入，模仿这个风格而不是客服腔：[贴 3 条真实例子]

**真实性检查**：生成后逐条问"用户真的会这么说吗？"凡是需要想象"某种用户可能这么说"的，删掉或改写。宁可小而真，不可大而假。

**让 AI 当挑刺的用户，不当出题的老师**：

> 你是一个挑剔的真实用户。你的目标不是验证流程，而是拿到能用的结果。看完这份输出，列出你还会要求返工的所有点。

出题老师角色产出服从度考卷；挑刺用户角色产出实用批评。
