# issues 冒烟集

工作流行为面测试（触发面见触发测试集.md，待真实语料补建）。断言：加载 issues 之后的正文分支行为与产物。
语料均为真实会话原样摘录或现场取证。跑法同其他 skill 冒烟集（干净会话发输入，查 skill 加载记录并观测产物）。

## 用例

- **S1**（老布局 mega 任务文件迁入 → 拆分，不保留汇总形态）：

  ```
  我曾要求agent归档和合并历史issue,这是其结果 docs/issues
  ```

  前置：现场有 `docs/tasks/` 老任务文件，单文件承载多份已完成任务（ey-timp-etl 现场为 413 行汇总视图，跨多个能力章节抄录验收断言与证据）。
  硬性：归位迁入时拆为多份 issue（一份一事）、已完成即按归档规则溶解为能力文件任务块；不把原文件整体平移保留为「任务视图」；迁入后 `docs/issues/` 下只余在办 issue 文件，不留任务壳。
  来源：2026-09-25 ey-timp-etl 78063e87（`docs/tasks/智能体节点.md` 原样搬为 `docs/issues/智能体节点/任务视图.md`，0 内容改动）+ 当日用户投诉（返工事件）。

- **S2**（非 issue 文件不入 docs/issues/ 与 features/）：

  前置：迁入/归档现场有设计文档、spike 验证报告与 issue 同目录。
  硬性：设计文档归 `docs/contexts/<限界上下文>/` 的 design（design skill 管辖）；spike/验证报告折入对应 issue 变更历史或 design；能力文件只收任务块，不收设计文档与报告。
  来源：2026-09-25 ey-timp-etl 现场（`archive/01_*_issue_design.md`、`archive/01_*_spike1.md` 与 issue 文件混置）。

- **S3**（一份一事：相关 bug 不合并为一单）：

  前置：同一现场排查出两个相关 bug（同一 case、同一修复设计覆盖）。
  硬性：各立一份 issue，blockedBy 或正文互链；不因「两者联动、由同一设计修复」合并为一份。
  来源：2026-09-25 ey-timp-etl 01 号单标题「（Issue 1/2 合并）」——合并后归档检索无法再区分两个根因各自的闭环证据。

- **S5**（评审修复方案在 issue 内，不另立文件）：

  前置：评审发现成立，本次变更已有 issue。
  硬性：方案写入该 issue「评审修复方案」。写可观察行为、不改什么、精确基线、验证命令。不写行号，不写步骤。不另写执行方案文件。归档时该节与当前位置等过程脚手架不进任务块（压为闭环结论并入验收结论）。
  来源：2026-10-09 用户裁定「执行方案写进已有 issue，不新建文件」。

- **S4**（不建索引：迁移/归档合并不豁免）：

  前置：归档迁移或合并操作完成。
  硬性：不建 README/索引文件；frontier 递归扫描 issue frontmatter 即队列视图。迁移助手类文件操作完即删，不留现场。
  来源：2026-09-25 ey-timp-etl `docs/issues/智能体节点/README.md`（自称「issues 索引」，列级别/来源/摘要/状态表）。

- **S7**（归档 = 溶解为能力文件任务块；首行 + 压缩公式四件）：

  ```
  现在的issue记录已经变得冗长甚至不可控了,有什么办法可以压缩,并保留每个关键决策来源
  ```

  前置：archive/ 存量任务壳臃肿（试点现场单文件 148 KB，验证记录叙述式誊写占约 90%），同能力任务散在多份壳里。
  硬性：归档终点是 `docs/contexts/<限界上下文>/features/<能力>_feature.md` 的任务块（不存在则创建，单任务能力也建），原 issue 文件删除不留壳；任务块 = 首行（bug 根因一句话含证据锚；enhancement 目标一句话）+ 压缩公式四件——关键决策（理由+放弃方案）、验收结论、显式出界、git 指针；变更历史不进任务块（git log 承担）；能力文件不复述 spec/design 契约；wontfix 块内标注、拒绝记忆迁入；编号只为在办服务（同上下文在办重号 → 晚创建者改最小空号 + git mv + 重写引用）。
  来源：2026-10-20 ey-timp-etl 试点返工（会话 ses_ea7b63f1；提交 e17061e6，12 文件 +114/-1084；148 KB→4 KB；用户裁定「合并成立」「issue=活着的工作，归档=溶解为能力文件任务块」「变更记录本身已经可以由 git 记录承担」）。

- **S8**（guide 机制废除 + 证据不落 docs/）：

  ```
  现在也反映出guide_issue开始逐渐变大无法控制,且其中没有有效信息的问题
  ```

  前置：ey-timp-etl 现场 guide_issue.md 57KB/308 行（状态表/覆盖对账已归档行只进不出、变更历史 100+ 条无出口）；`docs/issues/<限界上下文>/evidence/` 下 run_evidence.py 产物 2.7MB 被 git 跟踪（issue 80/82 已归档，证据仍留 docs）。
  硬性：不建 `guide_issue.md`——多 issue 拆分的排查结论与逐条断言归属结论（有主/已满足/出界）记对应 spec 变更历史；防孤儿断言核对在创建时按需重推（spec 断言 × 在办 issue 目标并集）；冷启动遇存量 guide_issue.md → 列出并提议删除，用户同意后执行。run_evidence.py 证据 JSON 按 implement 约定落主工作区的 gitignored 运行目录，不落 `docs/`；归档不自动删除证据。
  来源：2026-11-02/03 ey-timp-etl 现场 + 用户裁定「彻底删除 guide」（同时撤销 2026-09-24 裁定的收口全量评审）。
