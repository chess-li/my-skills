# Issue

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**一份 issue 承载一个需求或 bug 从创建到归档的完整生命周期，是人与 agent、会话与会话之间唯一的任务交接面。** 执行状态只写进 issue 文件，不另立平行产物——汇总视图、任务清单等把多份 issue 状态合并呈现的文件都算（平行任务文件 = 双事实源，必污染）。归档即溶解：issue 按压缩公式凝成任务块并入能力文件，不留任务壳。

护栏：

- 创建前检索：`docs/issues/`（在办）与 `docs/contexts/<限界上下文>/features/`（能力归档，含 wontfix 拒绝记忆）按概念检索，不只按请求措辞；命中 open → 更新既有 issue，不重复立项；命中 wontfix → 告知用户曾被拒绝及理由，用户坚持才新建
- 一份一事：一份 issue 只承载一个需求/bug；相关但独立的问题各立一份（blockedBy 或正文互链），不因「联动、同一修复」合并为一份；本条只约束在办生命周期——归档后身份从任务变记忆，同能力任务块合入同一份能力文件
- 书写三原则：耐久性优于精确性——issue 可能挂数周，创建期写行为契约与接口语义，不写会过期的文件路径与行号；执行期小节的实现指引用可 grep 定位的符号锚（类型/函数/字段/测试名）指代代码位置，不写行号——行号写入即开始腐烂、写错不挡执行者，符号锚漂移慢、写错可被执行者 grep 当场证伪（一次性验证记录例外）；行为式不过程式——写 what 不写 how，执行者自己重新探索；验收标准独立可验证，配「显式出界」清单
- 状态即事实：status 字段与实际进展一致，文件存在即在办（归档即删除文件，状态由任务块标题承载）；在办期流转即记变更历史，git 仓库改动即提交
- 本 skill 只管格式与生命周期：执行实现归 implement skill，bug 诊断修复归 debug skill

## 核心工作流

### 1. 创建

- 落 `docs/issues/<限界上下文>/<NN>_<需求名>_issue.md`（NN = 01–99，编号只为在办服务：取同上下文在办 issue、存量 archive 壳与 features/ 既有块号的最大号 +1；归档后编号随任务块退役。发现同上下文在办重号——并行会话撞号——晚创建者改最小空号、git mv、重写全部引用（blockedBy、正文互链），随当次改动同一提交。跨上下文需求落主导上下文目录，目标分别引用各 spec；项目已有任务存放约定则跟随），模板见下
- 子 issue 可带标量字段 `milestone: <milestone-id>`，一份 issue 最多归属一个 milestone；独立 issue 省略字段。ID 对应 `docs/milestones/<milestone-id>.md`，交付范围归 milestone skill。关联前读取旧值；已有其他归属且用户未授权改绑时，先交用户裁定，不覆盖旧值。归属变更写入该 issue 的变更历史。
- spec 收口的需求：先对照 spec/design 排查代码现状差距，排查结论随创建消息呈现；验收标准逐条抄入验收清单——抄入前逐条过断言，有多种合理解读或语义张力（含 design 原文措辞）→ 不照抄、不标注「执行期澄清」，停下路由来源 skill 澄清后再建，进队列的 issue 不携带未决语义；抄入时按验证可行性分家——验证依赖当前不可用环境/外部资源（真机、CI、他平台、live 模型、未建机制）的断言不混入主清单，各立一份 follow-up issue（目标引用同一 spec 节），主 issue 显式出界清单指向之：主 issue 只含当前可闭环条目；follow-up issue 以 open 入队列即进 frontier，环境未到位前由 implement skill 抓取前核拦下交用户裁定；门禁条目在创建期分家，不在归档期改判（改判 = 勾掉/降级条目；迁出为 open issue 续存不算改判，见归档节）；status: open 即入队列；验证手段留执行方预填
- 同一限界上下文内拆出多份 issue → 依赖只写各子 issue 的 blockedBy；排查结论（对照 spec/design 的代码现状差距）随创建消息呈现（同单份场景要求），并与其逐条断言归属结论（有主/已满足/出界）一并记入对应 spec 的变更历史——不建 `guide_issue.md`，不设母 issue、状态镜像或覆盖对账底账；后续批次的防孤儿断言核对在创建时按需重推（spec 断言 × 在办 issue 目标并集，结论同样记入 spec 变更历史）
- 创建完成后（单份或拆分整批）在当前上下文中做对比评审：issue 与现有 spec/design/代码逐面核对——验收清单抄录无失真、断言归属无遗漏（拆分场景，逐条断言求归属）、现状描述与代码一致；拆分批次加查子 issue 间交叉一致——认领与出界不互撞（同一工作一方认领、他方须出界）、blockedBy 不过宽（只列真实前置）不缺失（验收所依赖的地基已列）；发现失真当场修正再提交
- bug：category: bug；已知根因或修法只当线索写入「当前位置」，不作结论；红色回路的命令、关键输出、环境和最小场景写入 issue 的「复现记录」
- 有依赖：blockedBy 列阻塞方 issue 相对 `docs/issues/` 的路径（如 `插件化/01_代次地基_issue.md`）。爆炸半径大的机械性改动（wide refactor）不塞进功能 issue——单独立 issue 走 expand–contract（先并存、分批迁移、最后删除），每批一份

### 2. 队列与抓取

- frontier = 递归 `docs/issues/` 全部 issue：status: open 且 blockedBy 全部已消解（或路径不存在）；「还有什么可做」= 列 frontier，各附一句话目标
- 抓取 = status 改 doing + 变更历史记一笔；一个会话抓一份，抓完即开始：enhancement 走 implement skill，bug 走 debug skill
- 并行会话各抓 frontier 中的不同项；blockedBy 两路消解——阻塞方归档，或重估清空（被阻塞项所等的关键前置已合入基线/环境已具备，不等阻塞方归档）：重估清空 = blockedBy 改 [] 并在 frontmatter 注释行注记依据（等的是什么、何时何地已具备）

### 3. 归档与拒绝

- 归档 = 溶解，不是移动：issue 按压缩公式凝成任务块，追加进 `docs/contexts/<限界上下文>/features/<能力>_feature.md`（能力名 = spec 能力节名；不存在则创建，单任务能力也建）；原 issue 文件删除，压缩前全文由 git 历史承担；`archive/` 不再新增任务壳
- 任务块 = 首行 + 压缩公式四件：首行——bug 记根因一句话（含证据锚），enhancement 记目标一句话；四件：
  1. **为什么**——关键决策：功能/架构/业务决策各一条，含理由与放弃的方案；评审倒逼的约定写成决策的理由，不写缺陷过程；纯流程审批（授权、放行轮次）并入验收结论，不单列
  2. **证明了什么**——验收结论：通过条数、样本量/测试数、独立评审放行与日期；构建/测试切片折叠为一行（仓库回归测试即长期证据，不誊写 argv/指纹）；真实环境观测留提炼结论与证据位置/runId，接受指针日后悬空
  3. **没做什么**——显式出界，含未验证边界
  4. **去哪查**——git 指针（压缩前完整过程记录的提交哈希）+ 行为证据（回归测试名）

  变更历史不进任务块——git log 已承担；能力文件尾部可留一节「演进主线」（一句话串起各块因果链），除此之外不写
- 能力文件格式：frontmatter `type: feature-archive`（不进 frontier，状态由各任务块自记）；头部三节：分层定位（契约指 `../<限界上下文>-spec.md` 节号，不复述契约——复述即成双事实源）、来源清单（存量合并迁入时登记原编号+标题+归档提交哈希）、长期行为证据（回归测试名）；任务块按创建时间排，标题 `### NN｜标题（enhancement/bug → archived/wontfix，YYYY-MM-DD）`，原 issue 带 milestone 字段时标题行尾追加 `｜milestone: <milestone-id>`
- 实现任务：由 implement skill 第 7 步归档；条件在那边，独立评审范围与证据复用只由 code-review 判定，scoped 自检不放行
- 存量追溯拆分：归档前核对发现验收条目验证依赖当前不可用环境/外部资源 → 不勾不标绿，迁出为独立 open issue（目标引用同一 spec 节），本 issue 变更历史记迁出指向，剩余条目全绿后才归档——门禁条目以 open issue 形态留在 frontier，不在原清单勾销
- 拒绝：wontfix 同样溶解为任务块（标题标 wontfix，记裁定日期与理由）——拒绝记忆迁入能力文件，供创建前检索
- git 仓库：归档变更（能力文件追加 + 原 issue 删除）同一提交，提交前核对暂存区含全部内容变更

**Issue 模板**（frontmatter 与未标注小节由创建者填；标注「执行期」的小节由执行方填与更新）：

```markdown
---
status: open          # open / doing / archived / wontfix
category: enhancement # enhancement / bug
blockedBy: []         # 阻塞方 issue 相对 docs/issues/ 的路径；重估清空 = 改 [] + 注释行注记依据
# 归属 milestone 时取消下一行注释；独立 issue 删除该行
# milestone: <milestone-id>
---

# <需求名>

## 目标
<一句话>，满足 spec：docs/contexts/<限界上下文>/<限界上下文>-spec.md §<能力名>
基线分支：<建任务时检出的分支>（合并目标；非 git 项目省略本行；执行期）
提交区间：<起点 commit 哈希>..<任务分支名>（终点记分支名，不记顶端哈希——合入 squash 会改写哈希；归档时补记；非 git 项目省略本行；执行期）

## 验收清单
- [ ] <验收标准（抄自 spec）> —— 验证手段：<命令 / 人工确认步骤>（验证手段为执行期预填）
- [x] <验收标准> —— 已验证：<下方验证记录引用 + 结果>（YYYY-MM-DD）（执行期）

## 验证记录（执行期；追加，索引式记录）
- 每条一行：<ID> | <结论：退出码/样本量/关键输出一句话> | <证据位置+runId> | <执行来源：会话/评审轮次>；整轮不变的环境（JDK/构建工具/OS/依赖版本）只记一条「环境基线」，各条引用之；完整 argv、工作目录、输入指纹由证据 JSON（如 run_evidence.py 产物）承担，不誊写进本文
- 独立评审 <引用>：<精确基线/内容快照 + 完整或限定范围 + 实际重跑或复用的证据及来源 + 发现处置 + 裁决>；限定复审引用前轮完整评审及未变范围。来源与适用性判据归 code-review，不由记录自证

## 显式出界（创建时声明不做）
- <条目>

## 足迹（执行期）
- 仓库：<本任务触及的 git 仓库，含卫星仓库>
- 计划触碰：<文件/模块清单，供他方撞车预判求交>

## 当前位置（执行期，实时更新）
<下一步要做的事>

## 复现记录（执行期；bug 填写）
- 命令或操作：<已实际运行的复现手段>
- 输入与环境：<最小场景、地址或必要条件>
- 关键输出：<状态、错误、断言结果或响应体>

## 三面摘要（执行期；收口前填）
- 完整性：<通过 / 有发现 / 不适用 / 未验证 + 证据或原因>
- 正确性：<通过 / 有发现 / 不适用 / 未验证 + 证据或原因>
- 一致性：<通过 / 有发现 / 不适用 / 未验证 + 证据或原因>

## 变更历史（执行期；归档时不进任务块，由 git log 承担）
- YYYY-MM-DD 创建 / <状态流转或变更>

## 范围外问题（顺手发现，本次不修；执行期）
- <问题 + 位置>

## 评审自检（执行者交付或送独立复审前填；执行期）
- 本轮：<精确基线/内容快照 + 差异 + 验证记录引用 + 同类实例/所及文档核对 + 未完成项>
- 按 code-review 清单及适用场景逐项「已查 + 结论 + 可核查证据」；未变项注明前轮记录与快照引用，不写成重查（YYYY-MM-DD）

## 评审修复方案（执行期；发现成立时由 code-review 写入。没有未关闭条目可省略）
- 基线：<精确引用。前缀相同不算>
- 未关闭：<要改变的可观察行为>。不改：<显式保留>。验证：<命令>
- 已关闭：<行为> —— <独立复核记录引用 + YYYY-MM-DD>（执行者自报不作关闭依据）
- 未选：<互斥修法。用户未选时只列选项>
```

## 冷启动

项目没有 `docs/issues/` → 随第一份 issue 创建；`docs/contexts/<限界上下文>/features/` 随首次归档创建；不预建空目录、不建索引。现场存在 `docs/tasks/` 未归档任务文件或 `docs/issues/*.md` 平铺老布局 → 列出并提议按上下文归位迁入（补 frontmatter），用户同意后执行；任务已完成未归档 → 迁入即归档（按第 3 节溶解为任务块）；单文件承载多份任务的 → 拆为多份 issue 迁入，不保留合并/汇总形态；迁入后 `docs/issues/` 下只余在办 issue 文件。现场存在 `guide_issue.md` → 列出并提议删除（排查结论与断言归属改归 spec 变更历史承担、状态视图由 frontier 扫描取代），用户同意后执行。现场存在 `archive/` 存量任务壳 → 列出并提议按能力批量迁入 features/（合并 = 迁移：原件删除、能力文件来源清单登记原编号+标题+归档提交哈希），用户同意后执行；清点规则见 implement 归档合并节。已归档历史留 git，随时可溯。

## 完整示例（spec 收口到另一会话抓取）

- **现场**：订单 spec 更新收口，用户说"先记下来，下午让另一个会话做"
- **创建**：检索无重复 → 写 `docs/issues/订单/01_企业下单_issue.md`（status: open，三条验收标准抄入验收清单，显式出界：退款对接）
- **下午新会话**：用户说"看看有什么能做的" → frontier 只有企业下单（open、无阻塞）
- **抓取**：status 改 doing、记变更历史，走 implement skill 预填验证手段、补足迹
- **归档**（验收全绿、评审放行后）：凝成任务块追加进 `docs/contexts/订单/features/企业下单_feature.md`，git rm 原 issue，同一提交
