# 固定工作流与输入处理

## 1. 资料范围与优先级

按以下优先级处理事实：

1. 原始研发记录、原始检测报告、原始实验表和正式财务台账；
2. 原始立项申请、会议记录、技术方案、工艺文件、人员资料和成果证明；
3. 已形成的项目计划书、立项决议、成果效用说明和辅助账；
4. 用户口头说明或聊天补充。

低优先级材料可以补充上下文，但不能单独推翻高优先级材料。最终研发文档用于识别既有口径和对照冲突，不得把其中未经原始材料支持的宣传性表述自动升级为事实。

## 2. 递归盘点

建立 `资料清单`，至少记录：资料编号、文件名、相对路径、文件类型、资料类别、对应项目、覆盖年度、形成日期、可读性、主要用途、来源状态和备注。

资料类别固定为：

- 立项类：申请、可行性报告、会议纪要、决议、审批记录；
- 技术类：技术方案、工艺流程、设计图纸、配方、设备资料、专利和标准；
- 过程类：研发日志、实验记录、参数调整、失败记录、阶段总结；
- 成果类：检测报告、验收记录、样品/产品资料、应用证明、销售或降本数据；
- 财务类：辅助账、总账明细、工资、材料、折旧、无形资产、分摊依据；
- 人员类：研发人员名单、岗位、专业背景、工时、职责和社保资料；
- 其他：图片、扫描件、政策文件或客户说明。

忽略 `~$*`、`.DS_Store`、临时文件、输出目录和与当前项目无关的评估报告。批量输入时按最小项目单元建立项目边界，不因文件内容相似而合并项目。

## 3. 抽取方法

- DOCX：读取正文、表格、页眉页脚、标题层级和嵌入图片；
- XLS/XLSX：读取所有工作表、单元格显示值、公式、合并区域、图片和打印布局；金额必须保留原单位；
- PDF：提取文字并对含图表、扫描页和复杂表格的页面渲染复核；
- 图片：只记录清晰可见的文字、流程、样品、设备或检测结果；模糊处使用待补信息，不凭肉眼猜测；
- TXT/Markdown：逐段读取，重复段落去重但保留原始路径；
- 任何材料：同时记录文件路径、页码/表名/段落或表格位置，形成可追溯来源标记。

**内嵌图片取证**：文字提取对图片型内容返回空，必须先做取证再登记"不可读"——用 `scripts/extract_images.py` 把 DOCX/XLSX/DOC 中的内嵌图片逐张抽出并携带上下文（DOCX 取所在段落及前后文、最近标题；XLSX 取工作表名、锚点单元格及邻近非空单元格；DOC 按二进制签名凿取，页序即出现顺序），输出 `manifest.json`；加 `--ocr` 用 tesseract（chi_sim+eng）识别。OCR 文本一律按待核对处理，须结合上下文与图像本身确认后才可升为事实；取证发现图片损坏（如主体缺失、仅有页眉）时，登记损坏证据并向企业索取原件，不得凭残片猜测内容。

独立附件图片（单独存在的 `.jpg`/`.png` 等文件）是一等输入：可能整页就是一个附件而无任何环绕上下文，此时以文件名为主要语义线索，同样进入抽取与 OCR——**上下文缺失不构成跳过识别的理由**。

可使用 `word-template`/`word` 处理 DOCX，`excel`/`spreadsheet` 处理工作簿，PDF 读取与渲染能力处理 PDF。不要只依据文件名或封面推断内容。

## 4. 统一底稿

先建立一份统一研发活动底稿，再起草三份文档。底稿至少包含：项目名称、承担单位、负责人、背景与必要性、总体目标、技术指标、研究内容、技术路线、创新点、难点、不确定性、现有基础、人员与分工、周期与里程碑、预算与费用构成、预期成果、实际成果、应用效用、知识产权、第三方验证和资料缺口。

每个字段必须标注状态：

- `确认事实`：来源直接支持；
- `专业化表达`：仅改变表达，不增加事实；
- `冲突待核对`：至少两个来源给出不同值；
- `待补信息`：正式文档需要但来源不能确认。

**冲突裁决门禁**：凡标注 `冲突待核对` 且该字段会进入客户版正文的，生成前必须二选一：① 该字段落 `【待核对：Hxx】` 并把双方来源值记入底稿、编号登记补充信息清单；② 取得用户对该字段的明确裁定并在底稿记录裁定依据。未取得裁决前，不得把任一侧的值写入客户版正文——只在底稿留痕而正文直接取值，视同掩盖冲突。用户的裁定（如"以实际为准"）仅对裁定明确覆盖的字段生效，不得自动扩展到其他冲突项。模型无权代替用户在冲突值之间做选择。

## 5. 文档生成顺序

先完成资料清单和统一底稿，再按 JSON 输入协议调用 `scripts/generate_rd_docs.py`。脚本读取 `templates/report.json` 渲染清单，打开清单所列的 DOCX/XLSX 模板后填充全部产物；Word 页面稳定后生成补充信息清单 XLSX。不要先写三份正文再事后拼接事实，也不得用 Markdown 代替 DOCX 模板。

**生成前置检查**：确认底稿中所有 `冲突待核对` 字段已按第 4 节裁决门禁处理（落 `【待核对：Hxx】` 或经用户裁定）；存在未裁决冲突即调用脚本视为流程违规。

技术方案至少形成三条真实研发主线。优先按技术问题、研究对象、工艺阶段或不确定性归并；不是按文件数量分章。只有一至两个方向时，按真实阶段拆分；没有足够事实时保留占位，不人为填满三条主线。

## 6. 质量检查顺序

1. 内容检查：每个字段有来源或 `Hxx`；
2. 逻辑检查：目标、方案、里程碑、成果相互对应；
3. 合规检查：研发实质、排除活动、费用归集和备查资料；
4. 交叉检查：公共字段、时间、金额、人员、成果和编号；
5. 渲染检查：逐页检查 DOCX 和每个 XLSX 工作表；
6. 交付检查：文件名、页码、占位符集合和输出目录正确。

## 7. 受控扩展

若用户要求辅助账、A107012、A107041或其他申报表，先确认申报年度、适用政策、表单版本、财务数据、项目映射、分摊因子和会计口径。材料不全时只生成字段清单和待补事项，不生成带有虚构金额的申报文件。

## 8. 真实项目执行要点（2026-10 盖世食品 6 项目验证沉淀）

完整实战顺序：**对应表给用户审核 → 用户裁定归属与命名口径 → 逐项目事实底稿 → 生成 → 图片取证与核对 → 冲突裁定落地 → 重生成 → 跨项目汇总清单分派**。各环节要点：

1. **先对应表后生成**：多项目批量输入时，先由模型形成材料映射与待确认事项 JSON，调用 `python3 scripts/generate_correspondence_workbook.py --input <correspondence-data.json> --output output/研发加计/对应表与待确认事项清单.xlsx` 渲染工作簿，交用户审核（重点：项目归属、命名口径、材料缺口），裁定并记录后再进生成。批量场景禁止跳过此步直接生成。
2. **日期只到月份一律落 Hxx**：原始材料常见"2024年01月"这类月份级日期，不得杜撰具体日期凑合格式；年月信息记入底稿，具体日进补充清单。
3. **旧格式分路处理**：`.xls` 调用 `python3 scripts/extract_office_layers.py --input <file.xls> --output-dir <output-dir>`，脚本用 xlrd 读取工作表、输出文本与表格 JSON；`.doc` 先调用 `python3 scripts/extract_doc_layers.py --input <file.doc> --classify-only` 做二进制取证（文字层检索 + 图片签名扫描），读取输出的 `doc_forensic_result`，再分路——`readable` 或 `image_only` 调用同脚本并传入 `--output-dir <output-dir> --doc-forensic-result <结果>` 抽取内容，`damaged` 登记证据并向企业索取原件。分类证据会写出文字字符数、图片数量或无法抽层原因；不得笼统写"不可读"。
4. **图片证据链分级**：研发日志表单、产品标签、检测报告等高价值文档类图片逐张读图核对；样品/产品照片可按目录用途归类为成果照片并如实标注"未逐张核对"。OCR 误读字段（如许可证号）以读图为准；每次核对动作在 facts 留痕（哪张图、哪个版面、核对了什么）。
5. **裁定落地要处理关联字段**：用户裁定一个字段时，同一冲突源的关联呈现一并处理——如研发周期裁定取第 5 章值后，表 1 中被裁定的阶段行不再进入客户版正文，但完整留痕底稿；不得让被裁定一方的数据以其他字段形式残留在客户版文档中。
6. **汇总清单从底稿直读**：核验通过后调用 `python3 scripts/generate_supplement_summary.py --output output/补充信息汇总清单.xlsx`。单项目不传 `--batch`，脚本返回 skipped 且不创建文件；batch 场景待全部项目 facts JSON 就绪后，追加 `--batch --input <facts-1.json> <facts-2.json>`。脚本直接读取各项目 `supplements`（包含 word 与 list 两个通道），不反向解析产物文件；按责任部门与优先级排序，并生成分部门统计视图，便于一次分派补料。

**补充项双通道**：正文占位项使用 `channel: "word"`（缺省值），编号为 Hxx 且带最终 Word 页码；清单留痕项使用 `channel: "list"`，编号为 Lxx、没有 Word 页码。渲染器将 word 通道写入工作底稿和 04 清单，将 list 通道只写入 04 清单；DOCX 模板只接收 word 通道。核验脚本只校验 word 通道的 Hxx 集合与顺序，不修改任何产物。
