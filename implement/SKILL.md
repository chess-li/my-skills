# Spec 实现

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**目标与验收标准已在纸面，实现的职责是让每条验收标准通过，并让执行状态随时可被任何接手者续写。** 完成的定义是验收标准通过、已有声称未失真、且 code-review 判定的独立评审覆盖当前变更并可放行，不是"代码写完了"，不是 scoped 自检清零。归档是 issue 按压缩公式溶解为 docs/contexts/<限界上下文>/features/ 能力文件任务块（格式归 issues skill）；合入基线是另一件事。

实现护栏：
- 验收强制：每条验收标准对应一个验证手段，验一条记一条；未验证的验收标准 = 未完成
- 任务拆分留在会话内，不落盘；issue 只承载 issues skill 定义的执行期小节（目标、足迹、验收清单、验证状态、bug 复现记录、三面摘要、范围外问题、评审自检、评审修复方案），是执行的唯一交接介质（格式与生命周期归 issues skill）
- 偏差路由：触及 spec 断言或 ARCHITECTURE.md → 停下问用户；只触及 BC design → 按 design skill 先改文件再实现
- 范围：改动限于验收标准所需。顺手发现的范围外问题记入 issue「范围外问题」，不顺带修复或删除
- 代码质量：写生产代码前和切片提交前读取并应用 [code-quality.md](../code-review/references/code-quality.md)（code-review skill 的 references/code-quality.md，在 skill 安装目录，不在项目仓库）。写代码与评审代码共用该文件。不在本 skill 复述判据
- 测试质量：写测试前和切片提交前读取并应用 [test-quality.md](../code-review/references/test-quality.md)（code-review skill 的 references/test-quality.md，在 skill 安装目录，不在项目仓库）。写测试与评审测试共用该文件。不在本 skill 复述判据
- 失败契约：变更命中 [失败契约参考](../spec/references/failure-contract.md) 的读取条件时，写生产代码前读取全文。spec/design 已写字段实现进代码和测试。缺用户可观察结果走第 5 步，不在实现里补语义。不适用的字段写明原因。未读不得写该边界的代码
- 验证状态实时落盘，不依赖会话记忆——接手者可能是另一个模型
- 全部验收通过、已有声称未失真、独立裁决可放行 → git 仓库问三选一（合入基线 / 保留 worktree / 丢弃），合入或保留才归档。评审范围和证据复用条件只按 code-review 判定，scoped 自检不够
- git 仓库：worktree 内只改代码、issue 与前端对接文档（收尾刷新，见第 7 步），spec/design 修正一律回主 checkout；merge 基线分支只三处——取回修正、第 6 步评审前、合入前
- git 仓库：基线分支只收 spec/design/domains 文档提交，实现提交一律在任务分支；并行会话互不可见，协调只靠落盘状态——非主场 checkout 让出控制权前（turn 结束 / 等用户 / 切仓库）无未提交变更
- git 仓库：远端写操作（push、强推、删远端分支）须用户明示；合入、归档、squash 默认只到本地

## 核心工作流

### 1. 入口判断

- 消除已观察到的失败（含按诊断/修法/修改结论执行）→ 先 debug skill 复现并定位根因，再回来；本会话未定位根因不改代码
- 进度审阅与任务安排（「看看完成情况」「安排后续任务」类）→ 先盘点再排程：整批列出在途阻塞与未决决策（验收项的环境/外部依赖门禁、blockedBy 未解、待裁定设计），按 被 blockedBy 卡死 / 进行中 / 级联风险 / 待用户裁定 四层呈交，用户裁定后再排执行顺序；呈交清单收口时逐项对账——每项 = 已裁并落盘 / 显式放弃（记理由）/ 仍待裁（列入未决呈交），未裁项不静默消失；阻塞与裁定未清前，推荐推进方向是清阻塞与澄清，不是继续执行
- 抓取：`docs/issues/` 有 frontier issue（open 且 blockedBy 全部消解，归 issues skill 判定）且用户要开工 → 抓取前核验收可行性：验收清单含验证依赖当前不可用环境/外部资源（真机、CI、他平台、live 模型、未建机制）的条目 → 先列出交用户裁定（缩减范围 / 提供环境 / 保持 open 暂不抓取），裁定前不置 doing；无则抓取之（status 改 doing），读它，第 2 步接管
- 新实现：有就绪的 spec？ → 第 2 步
  - design 就绪：本次改动触及的值得固化的 how 问题未落定（BC design 或 ARCHITECTURE.md）→ 先走 design skill 落定再回来；改动不产生值得固化的决策 → 空满足
- 续写：`docs/issues/` 有 status: doing 的 issue？ → 读它。「评审修复方案」有未关闭条目 → 只执行未关闭，不查源会话补方案，不执行未选；条目已实现但未独立复核时，核对修复差异与验证记录后走第 6 步，不重复改代码。有未选 → 问用户，不代选。方案缺精确基线或要改变的行为 → 停下问用户，不按前缀相同的引用猜测。没有未关闭方案 → 按「当前位置」恢复执行。scoped 自检已清零 → 第 6 步独立复审，不得停
- 接手（续写、跨模型/跨环境移交）先复述：用自己的话在 issue 写「当前任务要达成什么、下一步怎么验证」；复述不出、断言读不懂或有歧义 → 停下问用户回 spec skill 澄清，不猜着动手

  ```bash
  git worktree list --porcelain   # git 仓库：按登记路径与实际分支定位任务 worktree，不按目录名猜分支
  ```
- 合入：用户要合入基线 → 「合入」节
- 皆否 → 只读或不改变行为与交付物断言的局部工作可直接干活；改行为或 spec 断言先走 spec，产生值得固化的 how 先走 design，再建/接管 issue；只改 HTML、解释页或其他面向用户的交付物时，至少派生临时验收清单后进入第 3 步

### 2. 建/接管 issue

写入 `docs/issues/<限界上下文>/<NN>_<需求名>_issue.md`（项目已有任务存放约定则跟随；现场存在 `docs/tasks/` 或平铺老布局 → 按 issues skill 冷启动迁移），模板与生命周期归 issues skill：spec 收口已发布 issue → 接管（预填验证手段、补足迹与当前位置）；没有 → 按其模板创建（status: doing）。本步规则：

- 逐条抄录 spec 的验收标准，为每条预填验证手段，优先级：可落成测试 → 该测试；其他可自动化的命令 → 命令；皆否 → 人工确认步骤
- 全称断言（无论/任意/所有/每个）按分支全集拆成逐项验证，一个实例测试不得给全称断言标绿；列不出分支全集 → 回 spec skill 补失败面枚举
- 条件子句含时序/生命周期状态（「执行后」「清除后」「重试后」、多跳链路）→ 验证手段须在真实序列造出该状态，不用单跳/注入态等捷径替代；捷径验过不给该条标绿
- 写不出验证手段 = 验收标准不可执行——回 spec skill 修正，不用模糊条目充数
- 跨上下文需求共用一份 issue，目标分别引用各 spec
- git 仓库：从基线分支（当前检出的分支）建 worktree：默认 `<项目根目录>/.worktrees/<需求名>`（用户指定位置优先；首次把仓库内 `.worktrees/` 写入 `.gitignore`），分支名 = 需求名，基线分支与起点 commit（建任务时基线顶端）记入 issue；创建前建立父目录并检查 `git worktree list --porcelain`、目标路径和分支占用，已有路径或分支先核对身份与未提交内容，不覆盖或重置；创建后核对登记路径 = 目标路径、实际分支 = 任务分支、HEAD = 起点 commit；接管时根据 Git 登记、已知任务线索与 issue 的起点记录核对身份及提交历史，存在不符先查明再继续。创建失败保留命令与错误，排除占用或权限问题后重试；实现在核对后的 worktree 内进行。跨仓库任务在每个触及的 git 仓库同样建 worktree（分支名 = 需求名），卫星仓库清单记入 issue「足迹」
- 撞车预判（git 仓库）：三查——① `git worktree list` 同基线在途任务 worktree，`git diff --name-only <基线>...<在途任务分支>` 求文件足迹交集；② 在途 issue 的「足迹」清单（递归 `docs/issues/`，含卫星仓库）与本任务计划触碰文件求交；③ 同基线 checkout 的未提交变更与未推送提交（他方裸作业信号）。任一面交集非空 → 重叠清单报用户定夺（串行 / 划分范围 / 仍并行），不静默并行；交集触及同一构建 artifact 的接口契约（如 dubbo api 模块）→ 默认串行
- 共享构建产物（`~/.m2` 等）不被 worktree 隔离：改他仓库 artifact 接口契约与同 artifact 在途任务不并行；确需并行 → 该任务用独立本地仓库（`-Dmaven.repo.local=<worktree>/.m2`）；install 前记录该 artifact 来源 commit，暂停/收尾时从基线重装还原

### 3. 拆分与执行

会话内拆成步骤逐个执行。粒度自定，唯一约束是覆盖全部验收标准。写生产代码遵循 tdd skill（测试先行）。变更命中失败契约读取条件时，先读失败契约参考，再写该边界的代码。

### 4. 验证与记录

每完成一条验收标准：执行其验证手段（无法自动化 → 请用户确认），把结果写入 issue（验证记录 = 索引行 + 证据 JSON 承载的可复现命令与关键输出摘录：测试计数/退出码/响应体；写不出命令与输出视同未验证不标绿；摘要如实报样本量——跑了几次写几次，外推 = 伪造），更新"当前位置"；提交前读取并应用 code-quality.md 与 test-quality.md 清本切片，并核对改动未超出验收标准；命中失败契约读取条件的切片还须已按该参考实现；有则本切片内清除，卫生不留给评审兜底；随后提交（git 仓库，含 issue）。失败 → 修复重验；重验仍失败 → 先回读 spec 断言原文对照理解再动手（纯猜重试禁止），是标准本身的问题 → 第 5 步；同一失败第 3 次出现 → 停下，把失败现象与已试路径报用户，不第 4 次猜。

可执行命令用本 skill 目录 `scripts/run_evidence.py run --output <本次独立证据路径> --criterion <验收引用> -- <原始 argv>` 执行。证据 JSON 是临时产物：落 gitignored 目录（惯例 `target/issue<NN>/`），不落 `docs/`——docs 只收提炼结论，归档后证据指针悬空是预期。issue「验证记录」按 issues 模板索引式追加（ID｜结论｜证据位置+runId｜执行来源），完整 argv、工作目录、输入范围与指纹由证据 JSON 承担，不誊写进 issue；验收清单引用该记录，当前位置只写下一步，不覆盖历史验证记录或替换原命令。

用同一脚本 `verify <证据路径>` 核对适用性；current 不证明真实运行、成功或验收覆盖，退出码 0 不自动勾选验收。默认保留输入范围；指定 `--input` 或排除非运行输入时写明理由，仍须覆盖真实源码、测试、依赖、构建/运行配置与数据，交独立评审核验。`stale`、`unknown`、来源缺失或环境无法核对时重新验证；不编辑旧记录或事后缩小范围来获取 current。

变更包含新增、修改、移除或改名/迁移时，读取 [变更种类验证](../spec/references/change-kind-verification.md)。判据只在该文件。

在 issue 的「三面摘要」小节收口前补摘要：完整性（每条验收标准和已声明范围是否覆盖）、正确性（验证是否支持目标行为）、一致性（spec、design、代码和交付物是否一致）。每面标记「通过」「有发现」「不适用」或「未验证」；缺少证据时写「未验证」和原因，不用空白或推断代替。

### 5. 偏差路由

- 验收标准互相矛盾、按字面不可实现、边缘情形推出荒谬 → 停下，向用户陈述偏差，裁定后走 spec skill 更新，再回来
- 发现 design 决策不适用：只触及本 BC design → 先改 `docs/contexts/<限界上下文>/<限界上下文>-design.md` 再实现；触及 ARCHITECTURE.md → 停下问用户
- git 仓库：上述 spec/design 修正回主 checkout 落盘（提交到基线分支），worktree merge 基线分支取回修正后继续

### 6. 归档前核对

全部验收标准通过后自动派首轮完整独立评审；修复后的范围由 code-review 判定，不询问是否评审：

- worktree 内先 merge 基线分支；带入新变更 → 重跑全部验证手段
- 跑项目的 lint/typecheck（如有）：本次改动引入的新失败 = 未完成，回第 4 步修复；既有的范围外失败 → 记入「范围外问题」，不顺带修复
- 读本次改动所涉 spec 章节与对应 design 决策（issue 引用的章节，不在 diff 里也要读），失真 → 第 5 步
- 交付自检：执行者每次交付或送独立复审前，读取评审维度清单及其场景文件（code-review skill 安装目录的 references/review-dimensions.md、code-quality.md、test-quality.md 等），按本轮范围逐项把「已查 + 结论 + 可核查证据」写入 issue「评审自检」，并随回报给出精确基线/内容快照、差异、验证记录引用、同类实例及所及文档的核对结果、未完成项。纯文字轮次的未变项引用前轮自检与快照，不冒充重查。只读清单、不读适用场景文件视同未查；任一项不过回第 4 步
- 委派交接：协调者核对上述产物，缺项退回执行者；回报或关闭记录与代码矛盾时，先按 code-review 第 3 步绑定同一文件/符号/快照核验意见，误报附反证更正，不把错误修法退回继续做。「全绿」「已派评审」或自报完成不能替代自检，也不作为独立放行依据
- 派 code-review skill，携带上述交接产物及 issue 提交区间。先核验意见成立性，再按其修复循环处理 P4 及以上；修复切片与验收切片同一提交纪律，提交前按 code-quality.md、test-quality.md 清切片，后回第 4 步。执行者只回报修复与验证，已关闭条目须附独立复核引用；仅 P5 报告后继续
- scoped 自检清零 → 立刻独立复审；完整或限定复审、证据真实性核验和复用均按 code-review，不能因自检清零归档或合入
- 独立评审记录覆盖当前变更且可放行：git 仓库 → 问用户三选一，不自选——合入基线 / 保留当前 worktree / 丢弃该任务。合入或保留 → 第 7 步（合入再走合入节）；丢弃 → 不归档、不改基线，移除 worktree（含删本地任务分支），删除 `docs/issues/` 该 issue。非 git → 第 7 步
- 交付终点证据闸：最终回复只引用 issue 中已经落盘的命令、退出码和关键输出。git 提交命令失败、`git rev-parse --verify HEAD` 无法取得提交哈希，或 `git status --short --untracked-files=all` 有未解释的 `M`/`??` 时，阻断“已提交/工作树干净/全部完成”的声明，并记录失败原因。交付含 HTML、CLI、脚本或其他运行入口时，必须按真实入口 smoke；静态检查不能替代交互、响应式、无障碍或运行时验证，无法运行则标“未验证”。

### 7. 归档

- 归档时的条目核对与任务块压缩按 issues skill 归档节执行
- 前端对接面刷新：本次改动触及前端对接面（前端可见的对外接口、字段、错误码增删改）→ 从 spec 断言与代码刷新 `docs/contexts/<限界上下文>/<限界上下文>-前端对接.md`（模板见下），随归档一并提交；未触及 → 跳过
- 补记终点（任务分支名，不记顶端哈希——合入 squash 会改写之）；归档变更同一提交：按 issues skill 归档节把任务块追加进能力文件、删除原 issue，提交前核对暂存区含全部内容变更，告知用户并附各条验证结果。不合入基线、不移除 worktree、不 squash

**前端对接文档模板**（派生视图，不新立断言）：

```markdown
# <限界上下文> 前端对接文档

> 派生视图：断言信源 = <限界上下文>-spec.md 与代码；改接口先改 spec，本文档只随任务收尾刷新。

## 接口
### <接口名>
- <METHOD> <endpoint>
- 入参：按媒体类型分档——formData 用表格（| 字段 | 类型 | 必填 | 说明 |）；JSON/XML 用对应代码块给真实示例
- 出参：同入参分档；JSON 用完整响应代码块，禁止散文摘要
- 错误码：始终用表格（| 码 | 含义 | 对接方处置 |）；「码」列写接口对外暴露给前端的错误取值，不写内部枚举名或常量名
```

## 合入

用户选合入基线或事后要合入时：

- 合入前核对独立评审记录是否覆盖当前任务相对基线的变更且可放行；缺失或已失效则先按第 6 步独立评审，完整或限定复审只由 code-review 判定。scoped 自检清零不够
- 同基线还有其他未归档任务 worktree 时，按 `git diff --stat <基线>...<各任务分支>` 从小到大排队合入，小者优先——小任务零冲突落位，冲突只由最大的任务解一次
- 任务分支合入 issue 记录的基线分支；项目走 PR 流程则改自动 push 任务分支并开 PR——用户选合入即授权推送，不再另行确认；非 PR 流程不自动 push
- squash 收口（git 仓库）：本需求从 spec 提交到归档提交的本地提交多于一个时，默认压缩为单个提交（执行后告知该序列）。常规走 merge 式——基线 checkout 上 `git merge --squash <任务分支>` 提交为单提交，`git diff <任务分支>` 为空作等价比对；要压入的序列含已落在基线上的提交（改写场景）走 patch 式——生成该区间 patch（`git diff <压缩起点> <旧顶端> --binary`）、基线分支改名 `<基线分支>-back` 保留、从压缩起点（序列首提交的父提交）重新检出基线分支、应用 patch 提交为单个提交、新旧分支 `git diff` 等价比对为空才删 `-back`；序列含已推送远端的提交 → 改写与强推须用户明示
- 移除 worktree（含删除本地任务分支）；走过 squash 先确认等价比对为空再移除
- 建议（项目仓库配置，非流程步骤）：`git config rerere.enabled true` 记录冲突解法供复现自动套用；合入前 `git merge-tree --write-tree <基线> <任务分支>` 不动工作区预判冲突

## 归档合并

同一上下文的存量归档壳累积多份，用户发起清点时：

- 逐份与 spec、design、现有代码核对：仍含有效检索记忆（关键决策、验收轨迹、拒绝理由）→ 按能力迁入 `docs/contexts/<限界上下文>/features/` 对应能力文件（合并 = 迁移：原件删除，能力文件来源清单登记原编号+标题+归档提交哈希；格式归 issues skill）；内容已全部过期/被替代/已消化 → 删除（git 历史保留）；wontfix 必迁入——拒绝记忆不删。按各归档的提交区间定位任务改动；区间悬空时（squash 改写或合入后分支已删）按起点哈希在基线日志定位本需求合入提交，定位不成以现存代码为据
- 不落汇总文件：能力文件是常驻检索记忆，「当前状态视图」由 frontier 与各在办 issue 即时生成——固化的汇总追 spec 改动必腐烂成双事实源
- 核对结论（迁入/删除文件 + 依据）随提交信息记录并随消息呈现给用户，不另存备查副本
- 核对发现的仍成立未完成/待办 → 列出并问用户是否现在完成；未批准不修（要修时各立一份新 issue，不回改归档文件）
- git 仓库：核对与迁入/删除后提交（执行后告知）

## 冷启动

项目没有 `docs/issues/` 时，随第一份 issue 创建（格式归 issues skill）；`docs/contexts/<限界上下文>/features/` 随首次归档创建。不预建空目录、不建索引。项目无前端对接文档而存量接口多 → 全量生成走 frontend-api-doc skill，不靠逐任务收尾补建。

## 完整示例（一次带偏差的实现）

- **现场**：用户说"spec 就绪了，开始实现企业下单"
- **入口判断**：`docs/contexts/订单/订单-spec.md` 有"企业下单"章节，`docs/issues/` 无对应 issue → 建 `docs/issues/订单/01_企业下单_issue.md`（status: doing），抄录三条验收标准并预填验证手段（两条跑命令，一条请用户人工确认审批流）
- **执行**：会话内拆成四步；实现中发现 design 的订单状态流转未覆盖审批分支 → 只触及订单上下文：先改 `docs/contexts/订单/订单-design.md` 再实现
- **验证**：两条命令验证通过并落盘；一条边缘标准（审批拒绝时订单自动取消）按字面不可实现——spec 未定义退款去向 → 停下问用户，spec 更新后继续
- **归档前核对**：所涉 spec/design 仍为真；独立评审覆盖当前变更且可放行（scoped 清零后仍独立复审）；可合入则问三选一
- **归档**：用户选合入或保留后，任务块追加进 `docs/contexts/订单/features/企业下单_feature.md` 并删除原 issue（同一提交），告知用户三条验证结果。不合入（选合入则随后走合入节）
