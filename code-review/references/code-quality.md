# 代码质量

写代码与评审代码共用本文件。判据只写在这里。

写生产代码前读取全文并应用。评审派遣时原文携带本文件。不适用的项写明原因。

## 判据

- 写与既有同类平行的代码（新 FormData、新枚举值、新组件）前，先读 2–3 个同类，对齐其结构、命名和错误处理。至少 2 个一致实例才算惯例。个例不强制对齐。先读文件，不凭记忆对齐。
- 同一行为已有实现时复用该实现，不并列第二份。
- 不留死代码。死代码包括注释掉的代码、未使用的导入，以及方法体未引用的参数。
- 生产代码没有仅为测试添加的方法、字段、类型或分支。想为测试开口子时，改设计（如注入依赖），不加测试专用物。本任务把既有生产代码变成仅测试消费时，删除该入口，或把测试迁到生产入口。
- 每一层、抽象和扩展点（接口、钩子、配置项、预留位）能指出当前消费者。指不出的不加。
- 发现复杂度时，先写出读者要同时持有的事实、变更扩散、隐藏依赖或重复推理。不以函数行数、类大小或模式数量单独判定复杂度。
- 对已命名的 smell 做最小处理。验证该处理降低了负担后停止。无关清理、投机泛化和顺手重写不随本变更扩张，另列范围外问题。
- 使用结构模式前，先写清责任、不变量、边界、耦合变化和当前消费者。只转发的层，或没有当前消费者的抽象，不加。需要检查表时读取 [责任先于模式](../../design/references/responsibility-before-pattern.md)。
- 所及类型和方法上的 javadoc 与类注释，其行为事实（日志级别、字段语义、成败路径）与代码一致。不一致则改注释或改代码。只核已有文字是否仍真：不把 design 写成代码镜像，不补写新注释。
