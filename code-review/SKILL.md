# Code Review

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**生成者不裁决自己的工作。** 变更是否可合入，由独立评审（新鲜上下文）的裁决说了算，不由实现者的自我评估说了算；scoped 自检只检查本轮修复差异，当前会话可做，不作裁决依据。

## 核心工作流

### 1. 派发评审者

派一个新鲜上下文的评审子代理，只给它这些：

- 目标与验收标准（来自 spec / issue / 用户要求；没有则写明本次变更的意图）
- 变更范围（精确基线、提交区间或变更文件清单，以及本轮内容快照；不能只写浮动的 HEAD）
- 代码位置
- 变更所涉 spec/design 路径（issue 引用的章节；没有则写明无）与验证记录位置（原始命令、输出、输入范围及指纹、执行轨迹引用）
- 流程内评审：执行者本轮逐项自检证据（来自 issue「评审自检」）；委派时由协调者核对，缺项先退回执行者，不把测试计数或「已派评审」当作自检。用户直接发起的 review 不要求补造实现期自检
- 评审维度清单原文（[references/review-dimensions.md](references/review-dimensions.md)）与第 3 步分级地板
- 代码质量场景文件原文（[references/code-quality.md](references/code-quality.md)）。写代码与评审代码共用该文件。维度清单里的指针不算携带原文
- 测试质量场景文件原文（[references/test-quality.md](references/test-quality.md)）。写测试与评审测试共用该文件。维度清单里的指针不算携带原文
- 变更包含新增、修改、移除或改名/迁移时，附上 [变更种类验证](../spec/references/change-kind-verification.md) 原文。没有行为去留时不附。新增路径成功不能单独完成该核对。

送审包用脚本钉死，不手工拼哈希：运行本 skill 目录 `scripts/review_package.py create --repo <被评审仓库或任务worktree> --baseline <精确基线> [--path <范围>…] --out <本轮评审目录绝对路径>`，产出三物——`snapshot.json`（逐文件 SHA-256 与 scopeSha256）、`review.diff`（相对基线的完整差异，含未跟踪新增文件，附 diffSha256）、`dispatch-scaffold.md`（派遣提示词骨架）。骨架已钉入基线、快照与 diff 的位置及哈希；目标与验收、spec/design 与验证记录路径、前轮评审记录位置（首轮填「无」）、发现落盘位置是 REQUIRED 槽位，填全才派发。快照钉当前工作区字节，未提交变更同样覆盖；评审者用 `scripts/review_package.py verify --snapshot <路径>` 复核无漂移。

送审包、评审报告与放行证据放 `<主工作区>/.agent-artifacts/<任务>/<唯一运行标识>/`，每轮新建目录，前轮只读；issue 引用绝对路径与哈希。主工作区从 `git worktree list --porcelain` 核对主 checkout，不放在待移除 worktree、构建清理目录或系统临时目录。首次创建前，在主工作区 `.gitignore` 加入 `/.agent-artifacts/` 并用 `git check-ignore` 核验。无 Git 仓库的非代码评审用项目目录，跳过送审包脚本和 Git 操作，在报告中明确范围与未验证项。评审者的可写范围只含本轮报告、核验记录与独立分配的一次性临时目录，不含共享父目录或历史证据；归档、合入与新一轮评审不自动清理证据。忽略规则不代表已有备份，删除保留材料须用户明确授权。

不给实现会话历史——评审独立于实现思路。原始工具执行结果是证据，不是实现思路，可以携带；实现者的叙述不替代它。评审者读代码与上述断言，不改代码。

产出要求：按本轮范围逐维度、逐场景给「已查 + 结论 + 证据」，无发现也写依据。限定复审的未变项引用前轮独立记录与内容快照，注明「复用」，不冒充本轮重查；不适用的项写原因。指针不算已查，不写没有依据的"看起来不错"。

报告开头增加三面摘要：

- **完整性**：意图、验收标准和已声明范围是否都有对应实现；没有适用对象时写「不适用」
- **正确性**：实现是否产生目标行为，测试与复现是否支持结论
- **一致性**：实现是否与 spec、design、项目惯例和交付物一致

每一面都写「通过」「有发现」「不适用」或「未验证」。无法检查时写「未验证」并说明缺少的证据，不把它写成通过。

第 2 轮起（修复循环内重派）：加带上轮发现清单、对应修复差异及上一轮独立评审记录；按第 4 步确定完整或限定复审范围，先验证上轮修复，再查修复影响与证据真实性。评审历史不是实现思路，独立性护栏不破；评级按第 3 步独立锚定，改判引用地板条款说理由。

### 2. 审阅与证据核验

未拆出的评审维度见 [references/review-dimensions.md](references/review-dimensions.md)。代码质量判据见 [references/code-quality.md](references/code-quality.md)，测试质量判据见 [references/test-quality.md](references/test-quality.md)。写代码、写测试与评审共用对应文件，不在维度清单复述。implement 第 6 步、tdd 写生产代码前和写测试前读取同一份。已拆出的场景只改场景文件；未拆出的维度只改维度清单。

每次评审（含限定复审）核验所引用证据：

- 逐条对照原始 argv、工作目录、输入范围与指纹、运行环境、退出码、原始输出和样本量；首轮独立重跑对应命令，允许一次运行覆盖多条声称。按相同测试选择器核对计数，不用另一组测试的计数差异判虚报
- 从宿主工具轨迹或独立执行的原始结果核对来源，不能只信实现者提供的 JSON、截图、哈希或「独立评审」标签。复用须有前轮独立核验记录与真实执行来源，且当前输入、环境和覆盖仍适用；输入范围是否完整也由评审核对。`run_evidence.py verify` 的 current 只证明记录范围内的内容适用性，不证明来源、成功或验收覆盖
- 缺少来源、输入或环境无法核对、原始输出与声称矛盾、疑似篡改 → 不复用，独立按原命令重新执行并记录。跑不了则标「未验证」并阻断通过；新运行不能把旧的虚假声称变成真实。核实伪造按第 3 步处理，不以压力、时间预算或纯文档修复豁免

独立核验结果追加到 issue「验证记录」（没有 issue 则写评审记录）：精确基线与内容快照、评审范围、实际重跑或复用的证据及其来源、发现处置和裁决。限定复审须引用前轮完整评审并说明未变范围；实现者回报不充当独立核验记录。

### 3. 发现与裁决

先核验整批意见，再形成修复方案：逐条绑定同一文件、符号和内容快照，重述要改变的行为，对照代码、测试、spec/design、平台版本与当前消费者核验适用性、保留行为和影响；另一文件的同名消费者不作反证。成立 → 分级；不成立 → 附反证，不写成「已修复」；有歧义 → 请求澄清，不部分实现。收到人或外部评审者意见也走本步，不另走一套流程。

成立的发现分级 P0（致命）/P1（严重）/P2（一般）/P3（轻微）/P4（低影响缺陷）/P5（非阻断建议）并附 file:line；验证声称伪造（核实虚报运行、输出或样本量）不低于 P0。实际运行但只验证 mock 或覆盖不足，按测试/行为缺陷分级，不因此判伪造；缺证据但未核实伪造时记「未验证」仍阻断。本任务引入的死代码、测试专用物（含退化形态，界定见 code-quality.md）、所及类型/方法上与代码矛盾的 javadoc/类注释（界定见 code-quality.md）不低于 P2；不以基线存在同类缺陷降权，基线同类实例同案列为发现。同模式缺陷归并为一条，列出全部实例及受影响的既有文档断言，修复针对这一类。只有证据真实且适用、独立评审覆盖当前变更范围、无未处理的 P4 及以上发现时才可合入；仅 P5 经报告不阻断。裁决必须与发现清单一致，不把 P2/P4 未处理项写成「不阻断」。

P4 及以上发现成立，且本次变更已有 issue：立即写入该 issue「评审修复方案」的未关闭条目（格式归 issues skill），写完该条才算已交付。写可观察行为、不改什么、精确基线、验证命令。互斥修法用户未选则写入未选，不写入未关闭。不写行号，不写步骤，不另写执行方案文件，不等会话结束再交接。修复须经独立复核确认后才标已关闭，并附核验记录引用；执行者自报完成不算关闭依据。P5 不写入未关闭。没有 issue 且用户要另会话修复：先按 issues skill 接上 issue 再写。只要报告、不要另会话修：不建 issue。

### 4. 处置与修复循环

按评审所处场景处置发现：

- 单纯 review 任务（用户直接发起的评审）：仅报告发现与修复建议，询问是否修复，不自动修复。
- 非单纯 review 任务（由 implement 等流程派发，如归档/合入门禁）：经第 3 步核验成立的发现全为 P5 → 可仅报告不修复；含 P4 及以上 → 自动修复，不询问。

每轮修复后由当前会话做 scoped 自检：逐项写出方案「要改变的行为」与「不改」两栏的可观察结果和验证证据，核修复对症、保留行为未丢、同类实例已清及所及文档同步，并按 code-quality.md、test-quality.md 查修复引入的新缺陷。缺任一栏证据不关闭发现；自检清零后立刻派独立复审，不停在自检结果。

独立复审默认完整，范围是当前任务相对任务基线的全部变更，不是相对前轮快照的修复差异。仅以下条件均由独立评审者核实时，改为限定复审：已有覆盖本任务的完整独立评审；此后只修正文档对已审行为/决策的描述，不改变行为契约、技术决策、代码、测试、依赖、构建输入或运行配置；相对前轮的差异与未变范围可由内容快照核对；前轮证据按第 2 步核验真实且仍适用。基线提交变化须核对差异，只有本次纯文字修正或内容不变的提交封装可沿用，其他变化做完整评审。任一条件不明也做完整评审。

限定复审只复核本轮文字修正、同类残留、与已审代码/契约的一致性及证据真实性；不重跑已独立核验且仍适用的命令，但缺证据或疑似伪造仍按第 2 步重跑。通过后，由独立评审者结合前轮完整评审给出覆盖当前范围的裁决。限定复审不是 scoped 自检，后者始终不能放行。连续两轮独立复审仍有阻断项 → 停下呈交未闭环项与已试路径，问用户。

### 5. 交付终点证据闸

评审结论和最终回复只能引用已经落盘的证据：issue/评审记录中的验证命令、退出码和关键输出。已有 issue，或用户要另会话修复时，P4 及以上发现没有对应「评审修复方案」未关闭或已关闭条目，不得写成已交付。涉及 git 时，提交命令非零、提交哈希无法由 `git rev-parse --verify HEAD` 取得，或 `git status --short --untracked-files=all` 仍有未解释的 `M`/`??`，都不得写成“已提交”“工作树干净”或“全部完成”；必须说明实际状态和失败原因。交付包含 HTML、CLI 或其他可运行入口时，按真实入口执行 smoke；只做静态解析不能推出交互、响应式、无障碍或运行时行为已验证，跑不了就标“未验证”。

## 护栏

- 完整评审与限定复审都必须独立：评审者与被评审实现不是同一会话，实现者自审不替代；scoped 是当前会话的修复差异自检，不作可合入裁决
