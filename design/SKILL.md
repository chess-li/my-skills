# 设计文档维护

## 意图锚点（每次使用前必读）

本 skill 守护一条主线：**动手之前，把"怎么构建"固化在纸面上，并让 design 里的断言持续为真。** design 是 how 层变更的第一现场：改技术决策，先改 design。但 design 刻意保持薄：只记录值得固化的决策，不是代码的镜像。

改动护栏：
- 先判断要不要 design 再动笔：不触及已有 design 断言、也不产生值得固化的新技术决策的，直接干活
- 尚未被用户接受的设计候选不写入本 skill 的文档。落点与撤除归 issues「临时方案」。用户接受后才按本 skill 写入
- 被指定的技术方案同样要评估：前提存疑或有明显更优选型时，先提出。用户尚未接受则只改「临时方案」，不在本步落盘
- 只写 how：what/why 与验收标准在 spec，引用不复制
- 决策归属范围定落点：归属单一上下文 → design；跨上下文或项目级 → ARCHITECTURE.md
- design 保持薄：只写"悄悄变了会有人受损"的技术决策
- 断言失真时只有两条路：决策仍被需要 → 更新它；已不重要 → 删掉它
- 上下文划分跟随 domains 文档；迁移跟随 domains 的变更时刻，不自行搬动

## 核心工作流

### 1. 入口判断

- 本条先于下面各条。接受只认用户原话：明确接受，或把方案指定为要落地的决策。要求讨论、写入 issue、先不改 design，不是接受。模型推荐不是接受。尚未接受 → 不进入第 2–6 步，不改 design 或 ARCHITECTURE.md。已有 issue，或用户要求写入 issue → 按 issues 写入或修订「临时方案」。没有 issue 且用户没要求写入 → 不创建 issue，不写 design。不因「带来决策」或「要改已有断言」进入写入。与现有断言矛盾时，矛盾留在已有 issue 的该节；没有该 issue 则只在回复中说明，不落盘
- 新改动：是否带来值得固化的技术决策（数据模型、对外契约、选型）？用户已接受 → 进入流程
- 改已有技术：是否改变 design 或 ARCHITECTURE.md 已写过的断言？用户已接受该变更 → 先更新 design。尚未接受 → 留在入口第 1 条
- 对应上下文还没有 spec → 先走 spec skill 完成 what/why，再回来
- 皆否 → 退出流程，直接干活

### 2. 归属路由

逐条决策判定落点：

- 决策可在单一上下文内独立完成与变更 → `docs/contexts/<限界上下文>/<限界上下文>-design.md`
- 决策的变更需要跨上下文协同或影响全局（技术栈、部署、跨上下文契约） → 项目根目录 `ARCHITECTURE.md`

### 3. 读现状

- 读对应 spec（what/why 的来源）、已有 design 与 ARCHITECTURE.md
- 选型/结构类决策列选项前先做先行调研：本仓库同类实现、上游依赖的对应机制、可得的社区参照实现；选项与推荐标注依据来源，未经调研不呈用户裁定
- 项目已有 `DOMAINS.md` → 先读，上下文划分跟随它；没有 → 先走 domains skill 冷启动判管辖，再回来
- 决策涉及分层、事务、仓储、映射、网关、服务层、事件、适配器、端口、聚合或其他结构模式时，先读 [责任先于模式](references/responsibility-before-pattern.md)，先写责任、不变量、边界和当前消费者，再命名或比较模式。
- 决策涉及外部调用、异步任务、超时、重试、队列、复制或派生数据、迁移、容量边界，或可能出现未知成功时，读取 [失败契约参考](../spec/references/failure-contract.md)；spec 仍拥有用户可观察结果，design 只落技术边界、权威状态/一致性、预算与隔离、重试/恢复/演进取舍。
- 决策涉及公共接口或数据边界时，读取 [接口与数据草图](references/interface-sketch.md)。没有这类边界时不读。用户已接受的契约写入 design，不把草图模板复制进每一份 design。未接受的回入口。

### 4. 写决策

- 只写用户已接受的决策。未接受的回入口，不在本步落盘
- 每条：决策 + 约束/取舍理由（为什么选它、放弃了什么）
- 数据模型与对外契约：记自己一侧，引用对侧，不复制
- 代码可读出的细节（版本号、配置项、私有函数）不进 design

### 5. 边界自查

- 逐条过筛：这个决策悄悄变了，会有人受损吗？不会 → 删掉该断言
- design 不含 what/why；与 spec 断言不矛盾
- 跨上下文、design 与 ARCHITECTURE.md 之间无重复断言
- 换视角通读：以第一次读本文档的下游消费者（无本会话上下文、能力可能低于你的实现者）视角逐节过——要猜的地方、有歧义的地方、缺的已接受决策，当场修掉再落盘。未接受的不在本步补进 design

### 6. 落盘

- 新建写入 `docs/contexts/<限界上下文>/<限界上下文>-design.md`（项目已有存放约定则跟随）；ARCHITECTURE.md 不存在时随首个项目级决策创建
- 更新在原文件就地修改断言，并追加一行变更历史
- 单文件大到难以维护时，在同目录按能力拆文件，命名 `<限界上下文>-design-<能力名>.md`，与 spec 拆分保持 1:1
- 语言跟随项目文档语言；无文档则跟随用户输入语言
- git 仓库：落盘后单独提交本次 design 变更，不与后续代码变更混合
- 写入后按 issues「临时方案」撤除：已接受的点从节内删除；没有剩余候选则删除整节（含标题）。标题还在 → 告知仍在讨论，不可进入实现。标题已不在 → 才告知 design 已就绪，可进入实现

**design 文件模板**：

```markdown
# <上下文名> 设计

## <能力名>

### 技术决策
- <决策> —— <约束/取舍理由>

### 结构与契约
<数据模型、对外契约：记自己一侧，引用对侧>

## 变更历史
- YYYY-MM-DD 新建 / 变更 <什么>
```

**ARCHITECTURE.md 模板**：

```markdown
# ARCHITECTURE

## <主题名>

### 技术决策
- <决策> —— <约束/取舍理由>

## 变更历史
- YYYY-MM-DD 新建 / 变更 <什么>
```

## 冷启动

不要一次建成体系：上下文的第一个值得固化的决策出现时建 design 文件，第一个项目级决策出现时建 ARCHITECTURE.md；此前不预建空文件、不建索引。

## 完整示例（一次跨两层的需求）

- **现场**：用户说"订单加个过期缓存，用 Redis。过期清理由消息队列统一触发。"
- **入口判断**：两句都是用户指定要落地的决策，视为接受，进入流程。模型另想到的方案不写入
- **归属**：Redis 选型与缓存结构归属订单上下文 → `docs/contexts/订单/订单-design.md`；过期清理由消息队列统一触发，这是用户指定的跨上下文决策 → `ARCHITECTURE.md`
- **写决策**：订单-design 记缓存数据结构、过期策略与取舍（一致性换性能）；ARCHITECTURE.md 记消息队列选型与理由
- **自查**：删掉"Redis 版本 ≥ 7"——依赖文件可读出，悄悄变了没人受损
- **落盘**：两份文件就地修改、追加变更历史。没有「临时方案」标题，告知用户可进入实现
