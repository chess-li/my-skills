# UI 极端数据验证

本 skill 守护一条主线：**从数据边界验证组件，而不是为了得到失败而改组件。** 先观察并报告，再决定修复。

## 核心工作流

### 1. 盘点渲染面

读取组件、页面、类型、校验 schema、数据库字段和 API 契约。列出每个渲染值、来源、类型、长度或数量上限，以及是否可选。包含标题计数、时间、徽标、按钮、头像、工具提示和列表长度。

### 2. 构造极端数据

从 [references/catalog.md](references/catalog.md) 选择真实可发生或 schema 支持的值。优先一个覆盖多种风险的 fixture，并按真实数据结构注入原有数据边界。适用时另外覆盖空列表、单条数据和大列表。找不到上限也要记录为「未定义」，不要编造限制。

### 3. 接入开发态开关

在 fixture、props 或 API stub 的边界切换数据。使用开发专用路由或 URL 参数，提供 `Demo`、`Worst case`，以及适用的 `Empty`、`One`、`Large` 状态。没有可运行项目时，生成自包含的开发态 HTML 作为观察载体。开关不得进入生产构建，也不得通过手改 markup 制造问题。

### 4. 观察边界

在组件真实容器宽度、`320px` 和支持的最大宽度下观察；支持时再检查 200% 缩放、深色模式和 RTL。使用浏览器截图或实际 DOM 结果。无法实际观察的结论标为推断。

检查文本、flex/grid、固定尺寸、徽标、数字格式、复数、缺省值、图片回退、翻译长度、滚动、列表性能，以及交互组件的键盘焦点、阅读顺序和可访问名称。每个问题记录数据值、出现条件和证据。

可访问性检查至少记录：每个交互控件能否用键盘到达、焦点是否可见、阅读顺序是否稳定、控件是否有可访问名称。性能检查只在有浏览器工具或项目基准时记录测量结果；没有测量工具时写「未测量」，不把主观感觉写成性能结论。

### 5. 报告并停止

先报告再修复。报告包含：

- **发生了什么**：按 `Broken`、`Ugly`、`Fragile` 分级，列字段、极端值、现象、原因、修复方向和 `file:line`。`Ugly` 只表示可观察的布局或可读性缺陷，不表示个人审美判断
- **需要裁定**：截断还是换行、空值显示、大列表分页还是虚拟化
- **保持正常**：已通过的边界
- **开关位置**：文件或 URL，以及可用状态

### 6. 用户要求修复时

生产组件需要修改时，先路由 tdd；若修复改变能力行为，先走 spec，若产生技术决策，先走 design。本 skill 只保留极端 fixture、观察结果和 UI 验证。完成路由后按项目现有组件和样式惯例修复，重新检查所有状态，包括 Demo 数据；确认修复没有改变正常数据的行为。保留最坏数据 fixture 作为开发态回归材料，除非用户要求删除。

## 默认授权

- 直接执行：读取组件和契约、构造报告、创建开发态 fixture 和开关
- 执行后告知：修改开发态演示文件、生成截图或报告文件
- 必须先确认：修改生产组件、删除现有 fixture、改变数据契约
